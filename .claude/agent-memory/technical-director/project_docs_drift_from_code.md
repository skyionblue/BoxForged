BoxForged's documentation has drifted from the codebase in ways that actively mislead. Verified 2026-08-19.

The sharpest example: both `docs/PROJECT_CONTEXT.md` and the GDD recorded the camera as Cinemachine offset `(0, 12, -8)` with a hard look-at. The actual prefab (`Assets/_Project/Prefabs/Core/pfb_CM_FollowCam.prefab`) has `FollowOffset: (7.879929, 11, -10)`, `FieldOfView: 40` — and an **undocumented −38.2° yaw**. Because `PlayerController` derives movement from camera yaw, that yaw silently rotated the entire control mapping. It was wrong for a whole phase and nobody caught it.

Other confirmed drift: planning material references "ground-indicator AOEs" that do not exist in code (there is no telegraph system at all); three scenes listed in Build Settings do not exist on disk; `CREATIVE_STATE.md` lists `LaundryTumbler` as a non-canon "thought" while it is live in a shipping scene.

A second sharp example (2026-08-19, B4/D3): the backlog described the two weapon-ability systems as duplicate stacks to be consolidated, implying ~81 `WeaponData` assets needed converting. Reading the assets showed the opposite — they are **stacked layers, not competitors**. `WeaponObjectSO.baseEquippedData` points *at* a `WeaponData`, so V3 is a live dependency of V4, and V4 supplies Epic/Legendary abilities only (`AbilityExecutor` maps Standard tier to `null`). The scary asset count was an artifact of the wrong mental model. **Beware summaries that count assets by type without checking which layer references which.**

A third example, and the cheapest to check (2026-09-01, ADR-0006 Fact 7a): `zone-layout-spec.md` sized World 2's shed at **3.0 × 8.0 × 4.2 m**; `pfb_env_bld_shedwithcrate` measures **~7.4 × 9.5 × 6.4 m** — roughly 2× on every axis. The spec's zone-1 width budget summed to exactly 16.5 m *because* it used 3.0 m; at the real size the zone was over-subscribed by 4.4 m and the fight floor absorbed it. Same class as World 1's `pfb_env_bank` at 1.9 m against a 7.6 m saloon (BACKLOG B-entry, fixed with a 4× scale). **A design-doc dimension table is an intent, not a measurement — measure the prefab's renderer bounds before summing anything against it.** Relatedly, `[ENV - Static]` in `Backyard_Dojo.unity` is at **yaw 45°** while its `m_LocalEulerAnglesHint` reads `(0,0,0)`, so the Inspector can display 0 for a rotation that is really 45°; the spec's §0 still claims the root is at identity.

A fourth example, and the most dangerous kind, because the drifted doc is a **completion note** (2026-09-01, B121): B116 reports *"Fixed by re-centring both at the new centre `(0,0,55.0)`"* for World 2's cherry tree. `git log -L` on the trunk's transform shows `z: 47.5` → `z: 62.53` — the opposite of a re-centring. The same note reports an M2 radial band of **9.65 m**, arithmetically `10.0 − 0.35` for a *centred* trunk; the built layout gives ≈ 2.1 m. So a validation reported as *measured* was *derived from the spec*, and a note describes a move as its own reverse. **A completion note is a claim, not a record.** The cheapest check is `git log -L <line-range>:<file>` on the exact transform it says it changed — under a minute, and it settles it. Where a note quotes a measured figure, cross-check it against the object positions it must have come from; if the arithmetic only works for a position the scene does not have, the measurement was not taken.

**But note the trap in the trap, because I fell into it.** Having found all that, ADR-0008's first version concluded the tree's position was a *defect* and specified moving it back. The owner then said the position was deliberate. **A doc/diff contradiction proves the records are wrong; it does not prove the code is.** On an authored asset — a placement, a scale, a dressing choice — ask the owner before deriving a fix from the doc. See [[cherry-tree-position-is-canon]]. The B121 half that survives is narrower and still worth having: the note is inaccurate about *what it did*, independent of whether the outcome was wanted.

A fifth pattern, found in the same 2026-09-01 re-measurement and worth generalising because it is a **measurement-method** error rather than a stale sentence: **`Renderer.bounds` is not a size measurement on this project.** It is a world AABB. On a `SkinnedMeshRenderer` Unity derives it by transforming `localBounds` through the **root bone**, so a rig whose `Hips` carries a non-yaw rotation inflates it; on environment meshes the 45° `[ENV - Static]` yaw inflates it. B119 published "the Grasscutter is 4.70 m tall, matching SpinCycle to the centimetre" from `bounds.size.y`; measured from baked mesh vertices the Grasscutter is **3.400 m** and SpinCycle is **4.251 m** — a 25% error, in a number that then drove an entire camera derivation. Measure from `sharedMesh.vertices` / `SkinnedMeshRenderer.BakeMesh`, transformed into the frame you actually care about. This is the same root cause as the `Renderer.bounds` warning in [[measuring-city-scene]]; treat it as project-wide, not city-specific.

Two more concrete instances from that pass, both "the doc asserts a validation that the scene cannot have supported": `Backyard_Dojo.unity` has **no baked NavMesh at all** (`m_NavMeshData: {fileID: 0}`, `CalculateTriangulation()` → 0 verts) while B116 reports `NavMesh.CalculatePath` `PathComplete` results in it (`docs/BACKLOG.md` B122); and the cherry tree's **canopy has no collider**, so every physics-raycast clearance sweep prescribed by ADR-0006 §Validation passes through 8.8 m of foliage and reports clear (B126). **When a doc quotes a physics or navigation result, check that the subsystem it queried actually has data in that scene.**

**Why:** on this project the docs *are* the AI's primary context, so a wrong doc propagates errors into every future session rather than just misinforming a human reader once.

**How to apply:** for any claim about architecture, camera, scene contents, or system wiring, verify against the actual prefab/scene/asset YAML or the C# before relying on it. Prefer citing file:line or asset values over prose in anything written back into the docs. Treat `PROJECT_CONTEXT.md` as intent, not as ground truth. And when the verification says a doc is wrong, decide whether the wrong thing is the record or the artifact before proposing a change to the artifact.
