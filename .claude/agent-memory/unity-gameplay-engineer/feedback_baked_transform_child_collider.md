Discovered 2026-09-01 building `Backyard_Dojo` Stage A (see [[project_backyard_dojo_build]]). Extends [[feedback_baked_transform_compose_rotation]] — that memory covers *overwriting* a baked root rotation when placing a prefab; this one covers two related but distinct failure modes that show up when *adding new components* to an already-correctly-placed prefab instance.

**Failure 1 — a child object added under a baked-rotation/scale prefab instance inherits the distortion.** `pfb_env_cherry_blossom_tree` ships with zero colliders. Adding a `CapsuleCollider` on a **new child GameObject** parented under the tree instance, with a small local offset (`localPosition (0, 2, 0)`, matching the trunk), landed at world `(0, 0, -152.5)` with `35×35×200` extents — because the tree's prefab root bakes `localScale (100,100,100)` + `localRotation (270,0,0)` (the same project-wide Meshy/Blender import convention as the rotation-only cases in [[feedback_baked_transform_compose_rotation]]), and the child's small local offset/collider dimensions got multiplied/rotated by that. **Fix: don't parent a new collider under such a prefab instance at all — add it as a sibling (same parent as the prefab instance) and place it directly in world space instead.** This sidesteps the inherited distortion entirely rather than trying to compensate for it, and is simpler to reason about than un-composing the parent's scale/rotation.

**Failure 2 — computing a `NavMeshObstacle.center`/`.size` (or any other component's "local space" field) from world-space `Renderer.bounds` via naive subtraction ignores baked rotation.** Adding `NavMeshObstacle` directly to the *root* of a `pfb_env_target_dummy`/`pfb_env_stone_lantern` instance (not a new child — the existing rotated root itself) and computing `obs.center = worldBoundsCenter - transform.position` treats that offset as if it were already in local space, when the object's real local space is rotated 270° about X. The result: the obstacle's Y and Z were silently swapped (an obstacle meant to sit `1.0m` above the object's feet, offset toward it slightly in Z, ended up offset in Y instead) — the obstacle still *existed* and had a plausible-looking size, so this does not show up as an error, only as a wrong-shaped carve. **Fix: use `transform.InverseTransformPoint(worldBoundsCenter)` for the center** (correct regardless of the object's rotation/scale), **and for `size`, explicitly account for a known 90°-multiple rotation** (a pure-270°-about-X bake, as all 7 non-pond dojo ENV prefabs share, swaps world Y↔Z: local size = `(worldExtents.x*2, worldExtents.z*2, worldExtents.y*2)`, not a straight `worldExtents*2`). Verify by printing the object's `lossyScale`/`localRotation` before trusting any hand-derived local-space math against it — never assume identity, per [[feedback_baked_transform_compose_rotation]]'s rule 1, and that rule applies to *every* local-space computation against these prefabs, not just placement rotation.

**General rule this generalizes to:** before adding any new component whose fields are defined in an object's local space (colliders, `NavMeshObstacle`, `NavMeshModifier` bounds, etc.) to or under an instance of one of this project's asset-pipeline-imported prefabs, check `transform.localRotation.eulerAngles` and `transform.lossyScale` first. If either is non-identity, either (a) parent the new object as a sibling and work entirely in world space, or (b) use `InverseTransformPoint`/proper rotation math, never a raw world-space subtraction.
