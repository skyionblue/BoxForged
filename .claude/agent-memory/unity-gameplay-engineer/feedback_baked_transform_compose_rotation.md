Discovered 2026-08-25 building `CulDeSac_WildWestCity` (see [[project_wildwestcity_build]], `docs/BACKLOG.md` B78). Placed 6 freshly-imported buildings (`pfb_env_bld_bank/stables/general_store/barber_shop/sheriffs_office/blacksmith_forge`, the B73 CulDeSac batch) using a plain absolute `eulerAngles = (0, yaw, 0)` per building, reasoning "the tool's rotation param is absolute, so this fully controls facing." Every screenshot taken (multiple angles, multiple buildings) looked like a plausible, upright, correctly-proportioned building — roof on top, door below, signage legible. **It was still wrong.** The owner, watching the live Editor directly, reported "laying on their side" / "scale doesn't match" — and was right: these 6 prefabs' actual default root transform is `localRotation euler: (270,0,0)`, `localScale: (100,100,100)`, `localPosition: (15,0,0)` (the position and scale parts were already known, see B73 — the rotation part was not). The `X=270°` is a necessary correction (the raw mesh is authored lying down / wrong up-axis); overwriting it with `(0,yaw,0)` doesn't just fail to fix facing, it removes the correction entirely, silently changing which raw mesh axis maps to world-up. `Renderer.bounds` confirmed this concretely: Bank's live height read `7.55m` with the naive fix vs its true `4.59m` at the correct baseline — a `BANK`-signage screenshot at the true baseline made the correct orientation unambiguous in a way the naive version's screenshot (still showing *a* door, *a* window — just the wrong face) did not.

**Why the screenshots didn't catch it:** these building meshes are boxy/roughly-symmetric enough that a wrong axis mapping still produces *something* that reads as "a building" at low screenshot resolution — a door-like dark rectangle, a window, a roof-like top edge — even though the actual face being shown is a side or back, or the whole thing is subtly the wrong height/proportion. A screenshot proves "this looks like a building," not "this is the correct building." Only a direct numeric comparison (`Renderer.bounds` before/after, or reading the prefab's own default rotation first) caught it.

**How to apply, for any prefab placement task:**
1. Before setting `rotation` on a newly-instantiated prefab, read its actual default `localEulerAngles` first (`PrefabUtility.LoadPrefabContents` + `go.transform.localEulerAngles`, or check a live instance's `eulerAngles` immediately after instantiation with no rotation override). Don't assume identity.
2. If the default is non-identity, **compose** the desired yaw on top of it rather than replacing it: `finalRotation = Quaternion.AngleAxis(desiredYawDegrees, Vector3.up) * Quaternion.Euler(bakedX, bakedY, bakedZ)`, applied via `transform.rotation` (via `execute_code`, since the MCP `manage_gameobject` tool's `rotation` param sets absolute eulerAngles with no compose option observed).
3. Verify empirically which world direction the "front" faces at `yaw=0` (screenshot from a couple of cardinal directions, or use the mesh's own readable signage/detail as ground truth — not just "it looks upright") before computing yaw for a full building roster.
4. Cross-check with `Renderer.bounds.size` — if a rotation is truly pure-Y, the Y (height) component of the bounds must stay constant regardless of yaw. If it changes, some other axis component snuck back to non-zero.
5. Trust a direct, hands-on owner observation of the live Editor over your own downsampled screenshot evidence — they can orbit/inspect in ways a fixed `manage_camera screenshot` call cannot, and "the screenshot looked fine to me" is not a rebuttal to "I'm looking at it right now and it's wrong."

**Confirms, doesn't contradict, prior art:** `CulDeSac_Room1_v2`/B74's log describes placing `pfb_env_bld_sheriffs_office` at "rot Y=90" and it reads correct there — almost certainly because that session's edit only touched the Y euler component (preserving the baked X), not because these prefabs are actually identity-rotated. Same underlying compose behavior, arrived at two different ways.

See [[project_wildwestcity_build]] for the scene this was found in, and `docs/BACKLOG.md` B78 for the full writeup including the older `pfb_env_bld_porchcabin`/`shedwithcrate`/`stacked_crates`/`train_sign` prefabs that share a related `(270,180,0)` baked default.
