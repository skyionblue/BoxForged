Learned 2026-08-26 fixing B99 in `CulDeSac_WildWestCity` (see [[project_wildwestcity_build]] eighth pass for the scene-specific numbers). Generalizes to any future "verify the player can/can't get somewhere" task.

**Use `Physics.OverlapCapsule` at the player's actual `CharacterController` radius/height, not `NavMesh.CalculatePath`, to verify player-reachability bugs.** NavMesh queries tell you where `NavMeshAgent`s (enemies) can path — a different collision system with a different radius (this project's baked agent radius, 0.5m, does not match the player's actual `CharacterController.radius`, 0.3m — always read the real component, never assume the two match). The player moves via physics collision against `Collider`s, so a physics-based check is the only one that actually answers "can the player stand here." Build a grid (0.4-0.5m step is usually fine) over the suspect area, mark each cell walkable via `Physics.OverlapCapsule(pointAtFeet, pointAtHead, radius, ~0, QueryTriggerInteraction.Ignore)` returning zero non-Ground hits, then BFS/flood-fill from a known-reachable seed (e.g. spawn) to find the true connected region. This works in Edit Mode against static scene colliders and in Play Mode against runtime state equally well — run it in both if the geometry involves anything that changes at runtime (carving obstacles, gates that toggle colliders).

**Always run a three-configuration control, not just "does the fix work now."** A flood-fill/BFS test can silently be broken (wrong seed point, wrong layer mask, an off-by-one in the grid bounds) and still report "not reachable" for the wrong reason, which looks identical to a correct fix if you only ever run the shipped-state case. Run:
1. **Fix disabled / bug reproduced** — confirms the test methodology actually detects the known-bad case (e.g. temporarily disable the new boundary collider and confirm the exploit area *is* reachable). If this doesn't reproduce the bug, the test is broken, not the game.
2. **Shipped state** — confirms the fix closes it.
3. **A positive control that should legitimately succeed** (e.g. disable the gates that are *supposed* to open on clear, simulating a normal cleared run) — confirms the test isn't just permanently returning "unreachable" by construction (wrong layer mask excluding everything, seed point itself unreachable, etc.).

Without step 3, a completely broken test that always reports "blocked" is indistinguishable from a correct fix. All three configurations should be run with the same code path (just toggling `Collider.enabled` + `Physics.SyncTransforms()` on the objects in question, restoring them after each measurement) so the only variable between runs is the thing being tested.

**Re-verify with the runtime/Play-Mode state when the bug involves anything that only actively resolves during Play Mode** — e.g. a carving `NavMeshObstacle` only carves while the carving system is ticking, so an Edit-Mode `NavMesh.SamplePosition` check against the statically-baked mesh will not reflect it. Enter Play Mode, let the scene's runtime bake (`LevelBuilder`-style deferred bake, or whatever this project uses) complete, and query against the live NavMesh, not an Editor-time snapshot. See [[feedback_editor_step_frozen_playmode]] for forcing Play Mode frames to actually advance between tool calls when needed.

See also [[feedback_circular_arena_clamp_sizing]] (a related but different reachability question — sizing a clamp, not proving a physical route is closed) and [[feedback_orthographic_camera_altitude_collision]] (another case where "trust the live query over the math" mattered).

**2026-08-26 addendum, zone-1-widening task in `CulDeSac_WildWestCity` ([[project_wildwestcity_build]] tenth pass): `Physics.OverlapCapsule` returning zero hits means "nothing here," which is true for both clear floor *and* true off-mesh void — a flood-fill grid that extends even slightly past the level's real collision footprint will find "walkable" cells in empty air with nothing under them, and BFS will happily route a "path" through them.** This produced a false-positive exploit report (boss zone "reachable" in the shipped, fixed configuration) on a re-run of this exact technique on a scene whose `Ground` plane had just been resized — the grid's south-end margin (added, same as always, to help detect wall placement) slipped past the new `Ground`'s true edge. A real `CharacterController` can't actually walk there (no floor, it would fall), so the flood-fill's answer was correct for the query asked and wrong for the question that mattered. **Fix: add a downward raycast ground-support check (`Physics.Raycast` from well above, straight down, confirm it hits the level's actual floor collider) as a second condition for "walkable," alongside the capsule-overlap check — or simpler, just bound the grid tightly inside the level's known true collision extent instead of padding it with margin.** Re-verify with the same three-configuration control either way; a methodology bug like this can hide behind a plausible-looking single-config result.

**2026-09-01 addendum, World 2 (`Backyard_Dojo`) Stage A build ([[project_backyard_dojo_build]]): in Edit Mode, `Physics.Raycast`/`OverlapCapsule` silently query stale collider transforms until `Physics.SyncTransforms()` is called — a scripted `transform.position =` change (moving/creating objects via `execute_code`, not through the Editor's own transform gizmo) does not propagate to the physics broadphase until the next physics step, which never happens automatically outside Play Mode.** A raycast/overlap run immediately after building geometry can report hits against objects at their *pre-move* positions (observed: a raycast at world origin reported hitting a lantern actually placed 47m away, and a capsule overlap reported hitting a cherry-tree trunk collider that had already been fixed and moved). **Call `Physics.SyncTransforms()` once after any batch of Edit-mode transform/geometry changes and before the first physics query that depends on them** — cheap, and skipping it produces results that look like real bugs but are pure staleness.

**Same task, second addendum: a downward ground-support raycast (per the addendum above) must also reject hits that are too *high*, not just confirm a hit exists.** The earlier addendum's fix (add a ground-support raycast so an empty-air cell doesn't read as walkable) is necessary but not sufficient near gates/walls: an unfiltered `Physics.Raycast` straight down through a `RoomGate`'s or wall's own `BoxCollider` (which typically spans floor-to-ceiling, e.g. Y 0–4) hits the **top** of that collider before it ever reaches the real floor at Y≈0 — and a flood-fill that then "stands" the test capsule on top of the gate/wall (well above its actual collision volume) finds it completely unobstructed, walking straight over the top of what should be a total barrier. This produced a false "no bypass" result that was actually "the test capsule is floating on top of every wall in the level." **Fix: after the ground raycast, discard any hit whose height falls outside the level's real floor-height band** (e.g. reject anything above the tallest legitimate walkable surface — an elevated deck/veranda counts, a 2.4m wall's top face does not) **before treating it as "ground."** Re-run the full three-configuration control after this fix, not just the shipped-state case — a methodology bug at this layer passes the "looks plausible" smell test just as easily as the margin/void bug in the addendum above did.

**Same task, a related but distinct lesson: near a `RoomGate` (or any object with a `NavMeshModifier(ignoreFromBuild)` plus a carving `NavMeshObstacle`), a `NavMesh`-based ring-sample and a `Physics`-based raycast sweep can disagree, and the physics sweep is the one that answers "is there real open floor here."** The gate's own footprint is permanently excluded from the baked mesh regardless of open/closed state (only the *carving obstacle's* hole heals when the gate opens — the modifier's exclusion doesn't), so `NavMesh.SamplePosition`/ring-sampling near a gate will show a "gap" that isn't a real physical obstruction. When re-verifying an open-floor/clearance requirement (e.g. a boss arena's minimum fight radius) near any gate, prefer a `Physics.Raycast` sweep against real colliders (matching how the original requirement was likely derived) over trusting a NavMesh-based check that happens to sample close to a gate line.
