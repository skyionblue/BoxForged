Discovered 2026-08-20 while live-testing `ForgePresenter` VFX in `CulDeSac_Room1_v2`. Save real tool-call budget next time by starting from these rather than re-discovering them by trial and error.

**`find_gameobjects`'s `search_term` is exact full-name match, not substring/contains, despite its description reading like a fuzzy search.** `"player"` (lowercase) returned zero hits against a real object named `"pfb_player"`; `"pfb_player"` (the literal full name) returned exactly one. Always pass the object's actual full name (including any `(Clone)` suffix Unity's default `Instantiate` adds — check the spawning C# for whether it renames the instance; if it doesn't, assume `"PrefabName(Clone)"`, no space before the paren, in Unity 6).

**Why to apply:** don't burn calls trying partial/fuzzy name queries against this tool — go straight to the exact name (grep the source/prefab for the literal `m_Name` or spawn-time naming behavior first if unsure).

**`manage_gameobject`'s `search_method: "by_name"` sometimes fails to find an object that `find_gameobjects` just found by the exact same string**, with no `by_id`/`instance_id`/`search_method` variant that works either (tried `by_id`, `instance_id` — both silently "not found" even for instance IDs known-good moments earlier). Root cause not fully isolated (possibly parentheses in `(Clone)` names, possibly something about deeply-nested runtime-instantiated hierarchies) — no reliable workaround found beyond falling back to reading the object's *authored* data (e.g. a `RoomDataSO`/`WeaponDropTableSO` position field) instead of querying the live instance. `by_name` **did** work reliably for scene-authored (non-`(Clone)`) objects at any nesting depth (e.g. `pfb_run_end_screen`, itself 2 levels deep under `[HUD]`), including toggling `set_active`.

**How to apply:** for objects spawned at runtime by `LevelBuilder`/similar (workbenches, props, enemies), don't rely on live name-lookup for their transform — read the authored ScriptableObject data asset for position instead, and drive the player to it directly.

**`manage_scene`'s `get_hierarchy` action ignores every attempted "which node's children" parameter** (`scope`, `path`, `root_path`, `target`, `instance_id` all either error as unexpected kwargs or are silently ignored) and always returns the top-level `scope: "roots"` listing — and that listing's `"total"` count does not reliably match reality; two consecutive calls returned different sets of exactly `total` items (some scene roots present in one response, absent in the next, with others swapped in). Treat `get_hierarchy` as unreliable for enumerating anything beyond "what are *some* of the scene's roots right now" — use `find_gameobjects` with exact names (found by grepping the source/prefab first) instead of drilling into hierarchy.

**`WorkbenchProp` (`Assets/_Project/Scripts/Systems/WorkbenchProp.cs`) uses a pure `Update()`-polled `Vector3.Distance` proximity check, not a physics trigger** — its own doc comment explains why: `CharacterController` without a `Rigidbody` doesn't reliably fire trigger events in Unity 6. This resolves the "not confirmed as a bug" flakiness noted in [[project_room1_v2_build]] about walking up to a real workbench not reliably opening `ForgePanel` — it was never a trigger/physics issue. It **does** gate on `Time.timeScale != 0`, so it will never fire while `RunStartUI`'s character-select screen (which sets `timeScale = 0`) is still showing and hasn't been dismissed via its real `Hide()` (deactivating its GameObject alone does not restore `timeScale`).

**`execute_code`'s own `Application.isPlaying` self-report is not trustworthy as a live status check** — it returned `False` immediately after a session of `manage_gameobject`/`find_gameobjects`/`manage_camera` calls that were all clearly still operating on a live, consistent Play session, and then returned `True` on a subsequent call in the same unbroken session with no `manage_editor play` in between. Don't treat one `execute_code` call's `isPlaying=False` as proof Play Mode ended — cross-check with a non-`execute_code` tool (e.g. `manage_gameobject` reading a value you know changed during Play) before concluding the session was lost. This refines (does not overturn) the older lesson in [[project_room1_v2_build]] that `execute_code` "appears to silently end Play Mode" — that still happens sometimes, just not deterministically on every call.

**`manage_camera` `screenshot` can return a visually stale/non-advancing frame across rapid successive calls in this headless automation session** — four screenshots requested across roughly a minute of real wall-clock time (spanning multiple tool round-trips) came back pixel-identical. Don't trust a single screenshot (or even several taken close together) to prove a multi-beat timed sequence is animating frame-to-frame; it can only reliably prove "this specific visual state existed at some point," which is still useful for yes/no visibility questions (does a VFX render at all, is a material transparent) but not for judging timing/feel — that needs the owner's own eyes on a real session, not automated screenshots.

**Update 2026-08-20 (B60 investigation): `find_gameobjects`' `search_term` returned zero hits for names later confirmed exact and correct** (`"RunStartUI"`, `"GameManager"`, `"StyleSelectPanel"`, `"HUD_Canvas"` — all real, exact `m_Name` values, confirmed via direct scene-file text search and later via live `execute_code` queries). This contradicts the earlier note above that exact-match queries work reliably — `find_gameobjects` returned `totalCount: 0` for every query tried in this session, including ones that should have matched by the tool's own description. Treat `find_gameobjects` as unreliable in general for this project's MCP setup, not just fuzzy-unreliable — don't spend calls on it; go straight to `execute_code` (see below) for anything beyond a scene's direct root objects.

**`manage_gameobject`'s `target` path parameter only resolves reliably one level deep from a scene root** (e.g. `"[Managers]/pfb_GameManager"` worked), and fails for paths that need to reach *inside* a prefab instance's own internal hierarchy (e.g. `"[HUD]/pfb_hud_v4/HUD_Canvas"` — the exact, confirmed-correct live path — returned "not found" at every depth beyond the first child). No workaround found for `target`-path lookups into nested-prefab-internal objects; fall back to `execute_code` walking `transform.Find(...)` chains or `GetComponentsInChildren<T>(true)` instead.

**`execute_code`'s C# snippets must NOT include `using` directives inline** (`"using UnityEngine; ..."` as the first line fails to compile with "Unexpected symbol") — write fully-qualified names (`UnityEngine.Resources.FindObjectsOfTypeAll<T>()`, `UnityEditor.PrefabUtility...`, etc.) instead, or presumably rely on pre-supplied usings if any (untested). Also, `UnityEngine.Object.GetInstanceID()` is treated as a hard compile **error** (not just a warning) under this tool's obsolete-API policy — avoid it entirely, there is no suppress; use object identity (name + hierarchy path) instead, or `PrefabUtility.GetCorrespondingObjectFromSource(obj)` + `UnityEditor.Unsupported.GetLocalIdentifierInFileForPersistentObject(sourceObj)` when you specifically need to resolve a scene instance back to the numeric local `fileID` its *prefab source* uses (this only works on the persistent source object, not the live scene instance directly — calling it on a scene instance throws "Input object must be persistent").

**Despite its limitations, `execute_code` was the single most reliable/precise tool this session** for anything beyond root-level scene queries: walking `transform.parent` chains to find exactly which ancestor was inactive, enumerating `Resources.FindObjectsOfTypeAll<T>()` across both scene instances and prefab assets in one call (distinguish by `go.scene.name == ""` for the latter), and live-editing state (`Undo.RecordObject` + direct field assignment + `EditorUtility.SetDirty`) when `manage_gameobject`'s own `modify` action couldn't reach the target path. Default to it early for any "why isn't X visible/active" investigation rather than working up to it through the other tools' failures first.
