`SpinCycleAI.DefeatSequence()` (CulDeSac_WildWestCity B103, 2026-08-26) played a multi-step death animation using scaled time (`WaitForSeconds`, `Time.deltaTime` accumulation) before calling `GameManager.TriggerWin()` at the very end. Because it was scaled, **any** system elsewhere in the scene that left `Time.timeScale` at 0 — for any reason, at any point after the killing blow — permanently stalled the entire sequence with zero error, zero timeout, and zero recovery. The boss visually died; the run silently never ended. Confirmed live: forcing `Time.timeScale = 0` before/through the kill froze the sequence indefinitely (~800 stepped frames, no progress); setting it back to 1 immediately resumed it.

**Why:** any code path whose only job is to end the run (a win trigger, a loss trigger, a required state transition) must not depend on `Time.timeScale` staying in any particular state, because timeScale is mutable from many unrelated places (UI pause screens, cutscenes, hit-stop effects, proximity-triggered panels) and there is no guarantee it will be 1 — or ever return to 1 — by the time your sequence needs to run. This codebase already has the correct pattern in several places (`ForgePanel.WaitForCutsceneThenClose`'s explicit "keeps advancing once per Update regardless of Time.timeScale" comment; `GameManager._waitRoomClearShow`/`_cutsceneStartDelay` are both `WaitForSecondsRealtime`) — the bug was an inconsistency, not a missing pattern.

**How to apply:** when writing or reviewing any coroutine that a game-ending or otherwise mandatory state transition depends on (win/lose triggers, required UI hand-offs, anything that must eventually fire no matter what), default to `Time.unscaledDeltaTime`/`WaitForSecondsRealtime` for its timing unless there's a specific reason the sequence should visually respect a pause. Don't assume `Time.timeScale == 1` will hold just because it was 1 when the sequence started.

**Secondary lesson from the same investigation, about the test environment itself:** after editing a script and letting Unity recompile mid-session (forcing a domain reload while Play Mode was being cycled via MCP tool calls), a `GameManager` field ([[project_wildwestcity_build]]'s already-known "UI screen SerializeFields resolved only via a Start()-time FindAnyObjectByType fallback" pattern) that read correctly-wired in the pre-edit baseline test read `null` in every post-edit test for the rest of the session, even though the target object was independently still findable and un-duplicated. Combined with other flakiness seen the same session (Play Mode ending silently between tool calls, an unrelated domain reload, a scene-data asset changing on disk outside any edit made) this was flagged as likely MCP/Editor session noise from the recompile rather than a real regression, and left for the owner to manually re-verify in a real Play session — but it's a real risk worth remembering: a mid-investigation recompile can leave the *rest of that same Editor session* in a degraded state unrelated to your actual code change. When a fix's verification shows something surprising and unrelated to the change you made, and it only started after your own recompile, treat a fresh Editor/Play session (not just another Stop/Play cycle in the same session) as the tiebreaker before concluding it's a new bug.
