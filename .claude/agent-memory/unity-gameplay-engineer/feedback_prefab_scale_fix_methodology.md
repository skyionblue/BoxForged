Found fixing B119 (Grasscutter boss 2x scale-up, 2026-09-01) in `pfb_enemy_grasscutter.prefab` vs `pfb_enemy_spincycle.prefab` (World 1's boss, used as the scale reference).

**1. "Compose, don't overwrite" ([[feedback_baked_transform_compose_rotation]]) is about non-identity BAKED values, not a blanket rule to always scale a child instead of the root.** That convention exists because overwriting a baked rotation destroys a needed correction. Before assuming a scale fix belongs on some "model root" child transform, actually read the prefab's current root `localScale` first. If it's plain identity `(1,1,1)`, there's nothing to compose against — setting it directly on the root is not "overwriting" anything. Checked the established precedent (SpinCycle, the very boss being used as the size reference) and found its OWN root transform is already at `localScale (2,2,2)`, not identity — i.e., the project's actual working pattern for this exact prefab shape (visual mesh + NavMeshAgent + Collider all as siblings/children under one root GameObject) is to scale the ROOT, with the collider/health-bar fields authored assuming that multiply. Matching the existing sibling boss's actual structure beat inventing a new "scale only the visual child" pattern from a rule that didn't apply to this case.

**2. Colliders (SphereCollider, CapsuleCollider, CharacterController) auto-scale with the GameObject's `lossyScale` at runtime — no serialized field edit needed when you scale an ancestor.** Confirmed live: Grasscutter's root `SphereCollider` (`radius: 0.55`, unchanged in the `.prefab` YAML) reads as an effective world radius of 1.1 m once the root's `localScale` became `(2,2,2)` — verified via `sphere.radius * root.transform.lossyScale.x` after `PrefabUtility.LoadPrefabContents`. `EnemyHealthBar` also auto-compensates: its `_offset` is applied as a `localPosition` (so it doubles in world height for free with the parent scale) and it explicitly inverse-scales its own bar's `localScale` by `transform.lossyScale` in `BuildBar()` so the bar's on-screen SIZE stays constant regardless of parent scale. Don't manually "fix" either of these after a root-scale change — check first whether the existing code already accounts for `lossyScale`.

**3. `NavMeshAgent.height`/`.radius` are literal, absolute values — never affected by transform scale — but check for an existing cross-model consistency decision before deriving them from a raw visual-scale ratio.** My first pass computed `radius: 1→2, height: 2.2→4.4` by literally doubling both to match the 2x visual scale. This directly contradicted an already-recorded, dated decision (`docs/BACKLOG.md` B114, 2026-08-31): "Grasscutter... should be built at radius `1` to match [SpinCycle]... for boss-to-boss consistency" — an explicit prior call that NavMeshAgent radius is a project-wide per-boss-type pathing constant, NOT something to derive from a model's visual bulk (the physical Collider is what's supposed to carry visual/physical bulk, per that same decision). Caught this only by re-reading `docs/BACKLOG.md`'s existing boss-related entries before finalizing the prefab edit — reverted radius to 1 (unchanged) and height to 4 (exactly matching SpinCycle, not a derived 4.4) once B114 was found. **Always grep the project's own backlog/ADRs for prior decisions about the exact field you're about to touch before deriving a "logical" value from first principles — a already-recorded, deliberate decision beats a clean-looking ratio.**

**4. `PrefabUtility.SaveAsPrefabAsset` on a `LoadPrefabContents` result re-serializes the WHOLE GameObject, materializing any previously-implicit script-default field as an explicit `.prefab` override.** After this fix, the diff included two brand-new lines (`_dashContactRadius: 1.5`, `_dashLaneFallbackLength: 20`) that were never touched — they were script fields added in an earlier session (B118) whose current-default values simply weren't serialized into this particular prefab yet. Confirmed harmless (values match the C# defaults exactly, no behavior change) but worth diffing carefully and calling out explicitly in the report/commit message so it doesn't read as an unrelated stray edit.

See [[project_backyard_dojo_build]] for the scene/session this was found in, and `docs/BACKLOG.md` B119 for the full writeup (including a newly-found, NOT-fixed corner-wall-clearance defect at the boss's current dormancy placement, unrelated to the scale/camera bugs themselves).
