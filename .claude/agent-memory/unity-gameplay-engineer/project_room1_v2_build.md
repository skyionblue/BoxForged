**2026-08-19: ADR-0002 RoomDataSO architecture implemented and first used by a new scene, `Assets/_Project/Scenes/CulDeSac_Room1_v2.unity`.** This is the first new World 1 room built since Sprint 0 (camera + telegraph) landed, and the first real use of the room-data-as-asset pattern ADR-0002 called for (see `docs/adr/0002-full-scene-rebuild.md`, `docs/BACKLOG.md` B3).

**Architecture (additive, old scenes untouched):**
- `Systems/RoomDataSO.cs` (new) — ScriptableObject: `roomName`, `maxConcurrentEnemies`, `bossOwnedWin`, `RoomSpawnPointEntry[] spawnPoints` (enemyPrefab + Vector3 position + facingY + spawnCount, all portable data, no scene refs).
- `Systems/LevelBuilder.cs` gained `RoomDataSO[] _roomData`, `GameObject _spawnPointMarkerPrefab`, public `RoomData` property, and `public List<EnemySpawnPoint> BuildSpawnPoints(RoomSpawnPointEntry[])` — instantiates one `pfb_EnemySpawnPointMarker` per entry, calls the new `EnemySpawnPoint.Initialize(prefab, count)`.
- `Systems/RoomManager.cs` gained `[SerializeField] LevelBuilder _levelBuilder` and `AppendRoomsFromLevelBuilder()`, called at the top of `Start()` — **pulls** from LevelBuilder (RoomManager calls LevelBuilder, not the reverse) specifically to avoid relying on Script Execution Order between two different `Start()` methods. `RoomData` (the old plain class) and the legacy Inspector-authored `_rooms` path are completely unchanged — old scenes with `_levelBuilder` left null get zero behavior change.
- New minimal prefab `Prefabs/Core/pfb_EnemySpawnPointMarker.prefab` (just an `EnemySpawnPoint` component).

**Room 1 content:** `RoomData_CulDeSac_Room1_v2.asset` (3 `WagonWheelRoller`s, maxConcurrentEnemies 2), `WeaponDropTableSO_CulDeSac_Room1_v2.asset` (JumpRope/GardenTrowel scattered, BikeHorn loot zone, 1 workbench, 2 cardboard piles, 9 ENV props). **B49 (NavMesh-agent timing) — A/B tested, and it is a REAL gap this room exposes, not a false alarm.** `"Failed to create agent because there is no valid NavMesh"` appears when `CulDeSac_Room1_v2` is the *only* loaded scene, and does **not** appear when `CulDeSac_Room1` (old) is the only loaded scene. Root cause found: `Assets/_Project/Scenes/CulDeSac_Room1/NavMesh.asset` — the vestigial pre-baked NavMesh ADR-0002 itself calls out as superseded — is still sitting on disk for every old scene and happens to supply valid (if stale) NavMesh data on frame 0, before `LevelBuilder`'s deferred bake (`BuildNavMeshDeferred`, one frame later) replaces it. A **brand-new** scene has no such leftover, so the real race — `RoomManager.Start()` spawns `NavMeshAgent` enemies synchronously, one frame before any NavMesh exists at all — is exposed for the first time. This will hit every future from-scratch room (2–5, boss), not just this one. Confirmed reproducible: loading the old scene additively (even fully disabled, not deleted) reintroduces the global NavMesh data and makes the warning disappear again in the same session. Recommended real fix (not applied — cross-cutting, outside this task): either have `LevelBuilder` bake synchronously/eagerly before any room activates, or have `RoomManager` wait for an explicit "NavMesh ready" signal from `LevelBuilder` before calling `ActivateRoom(0)`.

**Two self-inflicted incidents during this validation pass, both fully resolved — worth remembering the mechanics:**
1. `manage_scene` action `"save"` **ignores any `path` override and always saves whatever scene is currently active** — there is no save-as. Assuming otherwise (to "discard" a bad in-memory scene by saving it elsewhere) once emptied the real `CulDeSac_Room1_v2.unity` file to 0 GameObjects, and once wrote a harmless-but-real diff into the protected `ForgeLoop_Test.unity` (picked up new default field values from the `LevelBuilder` C# change — reverted via `git checkout`). **Always confirm the active scene via `get_active` immediately before any `save` call, full stop — never rely on a `path`/`scene_path` parameter to redirect it.**
2. `manage_scene` `close_scene`/`load` refuse to discard a dirty in-memory scene, and there is no discard override — `close_scene` needs an explicit `remove_scene: true` even when accepted, and a genuinely dirty scene can't be closed at all without saving it first. The only way found to isolate one loaded scene's content from another during a shared Play Mode session, without saving or losing anything, was `manage_gameobject` `set_active: false` on every one of its root objects.

**UPDATE 2026-08-19 — B49 fixed, plus a second real bug (B53) found and fixed while validating it. Full detail in `docs/BACKLOG.md` B49/B53.**
- **B49 fixed:** `LevelBuilder` gained `IsNavMeshReady`/`OnNavMeshReady` (set right after `BuildNavMesh()` inside the existing deferred coroutine). `RoomManager.Start()` no longer calls `ActivateRoom(0)` directly — a new `BeginRoom0WhenNavMeshReady()` waits for that signal first, and `Start()` now falls back to `FindAnyObjectByType<LevelBuilder>(FindObjectsInactive.Include)` when `_levelBuilder` isn't explicitly wired (same one-time pattern `GameManager` already uses for its UI screens), so the fix applies to old Inspector-authored scenes too, not just new RoomDataSO ones. Chose this over an eager/synchronous bake because the bake's one-frame defer is a documented *correctness* requirement (freshly-instantiated colliders need a frame to register with physics before `PhysicsColliders`-mode NavMesh collection sees them), not a performance one — forcing it synchronous would have reintroduced that bug. Verified in both scenes, isolated, via `execute_code` force-close (never saved the old one).
- **B53 found and fixed (separate bug, different files, NOT caused by B49):** the owner, watching Play Mode live, reported the camera not following the player in old `CulDeSac_Room1`. Traced to `CinemachineCamera.Follow` staying `null` — `CameraFollowTargetInjector.Start()` only ever tries `GameObject.FindWithTag("Player")` once, and scene root `Awake()`/`Start()` order is not guaranteed, so it can lose that race. This exact hazard is already known and documented elsewhere in the codebase (`RunStartUI.Awake()`'s own comment: "Awake() may have run before pfb_player was instantiated (scene object order)"), with its own lazy re-find in `Show()` as the existing precedent. Fixed `Assets/_Project/Scripts/Core/CameraFollowTargetInjector.cs` by adding the same retry pattern in `Update()`, self-disabling (`enabled = false`) once it succeeds. Confirmed via direct position tracking (not just console text) in both scenes, isolated, post-domain-reload.
- **Also found, explicitly not fixed (third, separate issue, own backlog entry B53's closing note):** `WagonWheelRollerAI.cs` has two real state-machine bugs that only surface during actual combat — `EnterPostAttack()` calls `_agent.isStopped` on an agent `EnterCharging()` already disabled, and `HitRollRoutine` isn't cancelled by `EnterDead()` so it can set velocity on a body that's already been made kinematic. Cosmetic Unity warnings, not exceptions; confirmed unrelated to B49/B53; worth its own small fix pass.
- **New tooling techniques that came out of this:** `execute_code` (via `UnityEditor.SceneManagement.EditorSceneManager.CloseScene(scene, true)`) reliably force-discards a dirty scene `manage_scene` refuses to close — see [[feedback_unity_mcp_scene_save_safety]] for the full write-up, including the important caveat that `execute_code` appears to silently end Play Mode if called while it's running (produced several confusing/contradictory readings before this was understood — don't use it to inspect *live* Play Mode state, only to set up before or clean up after).
