**Architecture (additive, old scenes untouched):**

- New minimal prefab `Prefabs/Core/pfb_EnemySpawnPointMarker.prefab` (just an `EnemySpawnPoint` component).

**B49 (NavMesh-agent timing) — A/B tested, and it is a REAL gap this room exposes, not a false alarm.** `"Failed to create agent because there is no valid NavMesh"` appears when `CulDeSac_Room1_v2` is the *only* loaded scene, and does **not** appear when `CulDeSac_Room1` (old) is the only loaded scene. Root cause found: `Assets/_Project/Scenes/CulDeSac_Room1/NavMesh.asset` — the vestigial pre-baked NavMesh ADR-0002 itself calls out as superseded — is still sitting on disk for every old scene and happens to supply valid (if stale) NavMesh data on frame 0, before `LevelBuilder`'s deferred bake (`BuildNavMeshDeferred`, one frame later) replaces it. A **brand-new** scene has no such leftover, so the real race — `RoomManager.Start()` spawns `NavMeshAgent` enemies synchronously, one frame before any NavMesh exists at all — is exposed for the first time. This will hit every future from-scratch room (2–5, boss), not just this one. Confirmed reproducible: loading the old scene additively (even fully disabled, not deleted) reintroduces the global NavMesh data and makes the warning disappear again in the same session. Recommended real fix (not applied — cross-cutting, outside this task): either have `LevelBuilder` bake synchronously/eagerly before any room activates, or have `RoomManager` wait for an explicit "NavMesh ready" signal from `LevelBuilder` before calling `ActivateRoom(0)`.

**Two self-inflicted incidents during this validation pass, both fully resolved — worth remembering the mechanics:**
1. `manage_scene` action `"save"` **ignores any `path` override and always saves whatever scene is currently active** — there is no save-as. Assuming otherwise (to "discard" a bad in-memory scene by saving it elsewhere) once emptied the real `CulDeSac_Room1_v2.unity` file to 0 GameObjects, and once wrote a harmless-but-real diff into the protected `ForgeLoop_Test.unity` (picked up new default field values from the `LevelBuilder` C# change — reverted via `git checkout`). **Always confirm the active scene via `get_active` immediately before any `save` call, full stop — never rely on a `path`/`scene_path` parameter to redirect it.**
2. `manage_scene` `close_scene`/`load` refuse to discard a dirty in-memory scene, and there is no discard override — `close_scene` needs an explicit `remove_scene: true` even when accepted, and a genuinely dirty scene can't be closed at all without saving it first. The only way found to isolate one loaded scene's content from another during a shared Play Mode session, without saving or losing anything, was `manage_gameobject` `set_active: false` on every one of its root objects.

**UPDATE 2026-08-19 — B49 fixed, plus a second real bug (B53) found and fixed while validating it. Full detail in `docs/BACKLOG.md` B49/B53.**
- **B49 fixed:** `LevelBuilder` gained `IsNavMeshReady`/`OnNavMeshReady` (set right after `BuildNavMesh()` inside the existing deferred coroutine). `RoomManager.Start()` no longer calls `ActivateRoom(0)` directly — a new `BeginRoom0WhenNavMeshReady()` waits for that signal first, and `Start()` now falls back to `FindAnyObjectByType<LevelBuilder>(FindObjectsInactive.Include)` when `_levelBuilder` isn't explicitly wired (same one-time pattern `GameManager` already uses for its UI screens), so the fix applies to old Inspector-authored scenes too, not just new RoomDataSO ones. Chose this over an eager/synchronous bake because the bake's one-frame defer is a documented *correctness* requirement (freshly-instantiated colliders need a frame to register with physics before `PhysicsColliders`-mode NavMesh collection sees them), not a performance one — forcing it synchronous would have reintroduced that bug. Verified in both scenes, isolated, via `execute_code` force-close (never saved the old one).
- **B53 found and fixed (separate bug, different files, NOT caused by B49):** the owner, watching Play Mode live, reported the camera not following the player in old `CulDeSac_Room1`. Traced to `CinemachineCamera.Follow` staying `null` — `CameraFollowTargetInjector.Start()` only ever tries `GameObject.FindWithTag("Player")` once, and scene root `Awake()`/`Start()` order is not guaranteed, so it can lose that race. This exact hazard is already known and documented elsewhere in the codebase (`RunStartUI.Awake()`'s own comment: "Awake() may have run before pfb_player was instantiated (scene object order)"), with its own lazy re-find in `Show()` as the existing precedent. Fixed `Assets/_Project/Scripts/Core/CameraFollowTargetInjector.cs` by adding the same retry pattern in `Update()`, self-disabling (`enabled = false`) once it succeeds. Confirmed via direct position tracking (not just console text) in both scenes, isolated, post-domain-reload.
- **Also found, explicitly not fixed (third, separate issue, own backlog entry B53's closing note):** `WagonWheelRollerAI.cs` has two real state-machine bugs that only surface during actual combat — `EnterPostAttack()` calls `_agent.isStopped` on an agent `EnterCharging()` already disabled, and `HitRollRoutine` isn't cancelled by `EnterDead()` so it can set velocity on a body that's already been made kinematic. Cosmetic Unity warnings, not exceptions; confirmed unrelated to B49/B53; worth its own small fix pass.
- **New tooling techniques that came out of this:** `execute_code` (via `UnityEditor.SceneManagement.EditorSceneManager.CloseScene(scene, true)`) reliably force-discards a dirty scene `manage_scene` refuses to close — see [[feedback_unity_mcp_scene_save_safety]] for the full write-up, including the important caveat that `execute_code` appears to silently end Play Mode if called while it's running (produced several confusing/contradictory readings before this was understood — don't use it to inspect *live* Play Mode state, only to set up before or clean up after).

**UPDATE 2026-08-20: `pfb_env_saloon_sign_board` removed from Room1_v2 — owner-confirmed, it was floating and redundant.** The saloon facade prefab (`pfb_env_saloon_facade`) already carries its own sign as part of its model; the separate `pfb_env_saloon_sign_board` prop was placed 2.3m away in X and 3.2m up in Y from the facade with no supporting geometry, reading as floating in air. **Confirmed working technique for forcing a scene to re-read a hand-edited `.unity`/`.asset` file when Unity already has it loaded:** `manage_scene`'s `load` action refuses if the in-memory scene is dirty (even from something as small as a prefab default changing under an instance). `execute_code` calling `UnityEditor.SceneManagement.EditorSceneManager.OpenScene(path, OpenSceneMode.Single)` directly bypasses that guard cleanly (no dirty-scene error) and reloads from disk in one step — this is the reliable version of the close-then-load two-step documented in [[feedback_unity_mcp_scene_save_safety]].

**UPDATE 2026-08-20: `CulDeSac_Room1_v2` at Play Mode start is NOT gameplay-visible immediately — two full-screen UI layers sit in front of it.** Confirmed by inspecting `Canvas` objects live: `RunStartUI` (character/gender/difficulty select, pauses `Time.timeScale=0`) shows first; even after calling its own public `Hide()` (restores `timeScale=1`, re-enables input, deactivates itself — safe to call directly, does **not** touch inventory/weapon state, unlike `OnStartClicked()` which likely does more and was avoided for exactly that reason), a second canvas, `pfb_run_end_screen` (sortingOrder 25, above HUD's 10 and even above `RunStartUI`'s own), was *already active* and fully covering the view with a solid background — not something that needs a "run" to actually end; it's just present in the hierarchy from scene start. A screenshot taken before dealing with both of these is a solid brown/tan full-frame image with no gameplay visible at all — this is not a black/empty-camera problem, it's these two canvases. `SetActive(false)` on `pfb_run_end_screen` (find via `FindObjectsByType<Canvas>`, match by name) got the real gameplay view back. Do this early in any future MCP-driven Play Mode smoke test in this scene, before concluding a screenshot "shows nothing" means something is broken with the camera/scene itself.

**UPDATE 2026-08-20: forge system (`ForgePresenter`/`WeaponTierGlow`) wired and live-tested for the first time — see `docs/BACKLOG.md` B24 for full detail.** New reusable pattern for testing forge/upgrade flow via `execute_code` without touching the real UI: `ForgeController.TryForge(bagIndex)`/`TryUpgrade(slotIndex)` are public and are the actual production methods (not a shortcut/mock) — calling them directly from `execute_code` on the live player's components exercises the real event chain (`OnWeaponForged`/`OnWeaponUpgraded` → `ForgePresenter.Dispatch` → real `WeaponHolder.Attach` → real `WeaponTierGlow.SetTier`), which is a legitimate way to verify a presentation system wired to those events without needing to simulate actual UI button clicks (no tool available for that here). Confirmed a real `WeaponInventory.WeaponSlots[i]` direct-index write also works from outside the class (public getter, private setter only guards *reassigning the whole array*, not mutating an element) — useful for placing a weapon into a slot without going through `AddToMaterialBag`/`TryForge` when you just want to test `TryUpgrade` in isolation.

**Important false alarm, now resolved — do not re-investigate if seen again:** `WeaponInventory.AddToMaterialBag` threw a `NullReferenceException` on `MaterialBag[i]` on the *second* attempt within one Play Mode session, immediately after a first attempt had succeeded cleanly on the same-looking call. This is **not a real gameplay bug** — it happened because `execute_code` had (once again, per [[feedback_unity_mcp_scene_save_safety]]) silently ended Play Mode between calls; `GameObject.FindWithTag("Player")` still finds the *Edit-mode* player GameObject sitting in the scene (a real object, just one whose `Awake()` never ran this session), so `MaterialBag` reads as never-allocated. Always confirm Play Mode is actually still running (e.g. `manage_scene get_active` — edit-mode `rootCount` is lower than the Play-mode-inflated count) before treating a sudden `NullReferenceException` from a previously-working call pattern as a real bug.

**UPDATE 2026-08-20 (later same day) — real root-cause lesson: "component activated" is not the same claim as "visually rendering," and don't stop investigating at the first plausible layer.** Owner played the real forge flow and saw the reveal text but not the Legendary glow this agent had reported working. The earlier "confirmed" screenshot was a hand-positioned close-up camera shot, not the actual live gameplay camera — that's the trap: a close-up proof shot can validate that a VFX *exists and is colored correctly* while saying nothing about whether it's visible at the distance the camera the player actually uses sits at. Traced the UI-vs-API call path first (`ForgePanel.Forge`/`Upgrade` call the identical `ForgeController` methods — no divergence, confirmed by reading the method bodies, not needed to re-prove live), then re-screenshotted from the *actual, unmodified live gameplay camera* at real distance — the glow was genuinely imperceptible. Root cause was two ordinary VFX-authoring mistakes, not a wiring bug: the glow materials were left at the default `_Surface: 0` (Opaque, depth-writing, no texture) instead of transparent/alpha-blended, and particle `startSize` (0.12-0.17m) was sized for a close-up shot, not this project's actual (very pulled-back, post-camera-yaw-work) gameplay camera distance. Fixed by copying an existing *proven-working* VFX material's exact blend/surface settings (`MAT_SpinCycleSparks.mat`, same shader) via the Material API rather than guessing shader keyword/queue values by hand, and by roughly tripling particle size. Re-confirmed fixed via the real camera, not another close-up. **General lesson: when asked to prove a VFX/presentation feature works, screenshot from the camera the player will actually use, not a custom positioned one — a close-up shot proves existence, not visibility, and those are different claims.**

**Also noticed during this investigation, not confirmed as a real bug:** driving `WorkbenchProp`'s real proximity trigger (teleporting the player near the actual workbench GameObject) did not reliably open `ForgePanel` even after confirming a fresh `PlayerInRange` transition and confirming `Open` was subscribed via reflection on the event's invocation list. Not chased further — plausibly a raw-teleport-vs-`CharacterController` artifact of this testing method rather than a real bug, since the owner's own real session clearly got the panel open and used it. If this resurfaces, a real (non-teleported) walk-up test would settle it either way.

**RESOLVED 2026-08-20: `WorkbenchProp` is not trigger-based at all.** Read the source directly this time — it's a pure `Update()`-polled `Vector3.Distance` check, explicitly because `CharacterController` without a `Rigidbody` doesn't reliably fire trigger events in Unity 6 (its own doc comment says so). So the earlier flakiness was never a trigger/physics artifact. It does gate on `Time.timeScale != 0`, so it silently never fires while `RunStartUI`'s character-select screen is up and hasn't been dismissed via its real `Hide()` — deactivating its GameObject directly (done this session, see below) does not restore `timeScale` to 1.

**UPDATE 2026-08-20 (owner feedback pass): timing too fast + zero particles during anticipation/transformation + above-head anchor experiment — full detail in `docs/BACKLOG.md` B24.** Summary of what changed, since it's the kind of thing worth knowing before touching `ForgePresenter.cs` again:
- Confirmed by reading the code directly (not guessing): the anticipation/transformation beats never had any particle VFX at all — pure transform tweens on a ghost mesh and the weapon's own transform. The only VFX anywhere in the forge feature was the persistent `WeaponTierGlow`, a different system entirely.
- Found a fully-authored, completely orphaned particle prefab, `Assets/_Project/Prefabs/VFX/pfb_forge_vfx.prefab` (gold rising-spark burst), referenced by nothing in the whole project, whose material (`MAT_Spark.mat`) had the exact same Opaque/no-alpha-blend bug already found and fixed once this sprint for the tier-glow materials, plus undersized particles. Fixed both (Material API + ParticleSystem API, mirroring `MAT_SpinCycleSparks.mat`'s proven settings — not hand-edited YAML) and wired it into both beats via two new `ForgePresenter` fields.
- Widened every beat duration (anticipation 0.35→0.8s, transform 0.5→0.9s, bloom/reveal durations similarly) and pushed the new values directly onto `pfb_player.prefab`'s live component (not just the C# defaults) — this project has hit the stale-prefab-serialization bug (B8/B9/B39) often enough that verifying the actual serialized value on disk is now the default move, not an afterthought.
- Added a togglable `PresentationAnchor` (`WeaponMuzzle` vs `AboveHead`), defaulted to `AboveHead` (2.1m above the player's feet) per the owner's own reasoning about the post-B27/B59 pulled-back, yawed camera making hand-height easy to miss.
- Live-verified via the real `ForgeController.TryUpgrade` (same method `ForgePanel`'s button calls) on a Legendary-rarity weapon (BikeHorn — GardenTrowel is Rare-capped at Epic and can't be used for this test): a screenshot from the real, unmodified gameplay camera showed a new gold particle cluster that wasn't present before the trigger. Could not get a literal UI-click walkthrough this session (blocked on `RunStartUI`'s character-select screen with no UI-click tool available; worked around by deactivating `pfb_hud_v4` directly to unblock the camera for screenshots) — see [[feedback_unity_mcp_gameobject_lookup]] for the tooling detail.

**CONFIRMED ROOT CAUSE OF B60 (docs/BACKLOG.md), found the same day:** that `pfb_hud_v4` deactivation above is exactly what broke `RunStartUI` for the owner afterward. It was never reactivated before the session ended, and — per [[feedback_play_mode_no_revert]] — this project's Editor does not revert Play-Mode-adjacent `SetActive` changes on Stop, so the disabled state sat in the live, *unsaved* scene (zero `git diff`) until the owner's next fresh Play session, where the whole HUD (including every `RunStartUI` panel, all still correctly wired and still correctly receiving `Show()`) silently failed to render. Fixed by re-enabling `pfb_hud_v4` and saving. **Lesson for next time a UI screen blocks headless testing: prefer disabling only the specific blocking panel/canvas (or driving it via its own public API, e.g. `RunStartUI.Hide()`/`OnStartClicked()`) over deactivating a shared ancestor several levels up (`pfb_hud_v4` is the parent of the entire HUD, not just the blocking panel) — and explicitly re-enable whatever was disabled before ending the session, since it will not revert on its own.**
