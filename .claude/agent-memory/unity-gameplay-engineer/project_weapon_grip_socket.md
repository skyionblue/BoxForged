**RESOLVED 2026-08-20 (round 3)** on `feature/sprint-0-foundation-rebuild`. Three rounds same day: round 1 tuned `WeaponGripPoint`'s position+rotation on Cowboy/Ninja Male but left the per-character `WeaponData` duplication in place, and "verified" with a weapon that silently bypassed the mechanism under test; the owner then tested for real and found Ninja Male (and Ninja Female) still broken. Round 2 found the double-offset root cause and retired the duplication, but its own re-verification only checked grip *distance* numerically and eyeballed rotation on the bostaff alone — round 2 declared "RESOLVED" while the rotation was still actually wrong on both characters. Round 3 (this entry) found and fixed the real rotation bug. Full writeup and the new-character checklist live in `docs/BACKLOG.md` B63 — this memory is the condensed "what to know before touching weapon grip/attachment again" version.

**Round 3 finding:** `WeaponGripPoint.localRotation` on `pfb_char_cowboy.prefab` and `pfb_char_ninjamale.prefab` was simply the wrong value — `(324.54, 197.41, 203.77)` Euler, identical on both, and not derived from either character's actual rig. `pfb_char_cowgirl.prefab`'s socket (confirmed correct, never touched) uses `(10.16, 186.79, 141.24)` Euler — mathematically the *same rotation* Cowboy/Ninja Male needed. Verified empirically in Play Mode against three shared weapons (bostaff, sixshooter, katana) on both characters via the real `WeaponHolder.Attach()` path, screenshotted from the actual Game-view camera at multiple angles: the sixshooter now holsters naturally at the hip (matching Cowgirl's own hold), the bostaff hangs/rests naturally, the katana points forward from the grip. Comparing each character's `LeftHand`-relative-to-`LeftForeArm` *local* rotation confirmed Cowboy/Ninja Male/Cowgirl all share the same rig convention — Cowboy's hand only *looked* differently oriented in world space because his current idle/armed stance (raised boxing-guard fist) differs from Cowgirl/Ninja Male's relaxed idle, not because of a rig-axis difference. Fixed by setting both prefabs' `WeaponGripPoint.localRotation` to Cowgirl's value (byte-identical quaternion, confirmed via git diff); `localPosition`/`localScale` were left untouched since the owner had already confirmed position was correct.

**Why round 2's verification missed this — a second, distinct instance of the same failure family as [[feedback_verify_test_exercises_path]]:** round 2's "numeric sweep across all 19 weapons" checked weapon-origin-to-socket *distance* only, not rotation. The one weapon spot-checked by eye for overall look (the bostaff) is symmetric and was held roughly centre-gripped and horizontal — a pose that still reads as "plausible" even with the wrong rotation applied, because a staff held sideways doesn't obviously look broken the way a directional weapon does. Equipping a **sixshooter** (small, asymmetric, directional) immediately exposed it: the revolver floated disconnected up near the shoulder/collar. Lesson generalizes beyond this bug: a symmetric/ambiguous-shape test object can make a visual "looks fine" check pass even when the underlying transform is genuinely wrong — pick (or include) a test case whose shape would visibly betray the specific class of error you're checking for, not just any representative instance.

**The round-1 mistake, worth internalizing:** round 1's "verification" weapon (`WeaponObject_BikeHorn`) had no per-character variant, so `WeaponCycler.ResolveWeapon` was silently falling back to the shared asset — round 1 never actually exercised the mechanism it claimed to validate. **Lesson: when validating a per-character or per-variant resolution path, confirm via logging/inspection that the test case actually resolves through that path, not just that the visual result looks right** — a correct-looking result can come from accidentally bypassing the exact thing under test.

**Round 2 real root cause:** the `Cowboy`/`NinjaMale` variant `WeaponData` assets' grip offsets were hand-tuned back when `WeaponGripPoint` was still identity. Once round 1 gave the socket a real correction, every variant asset's offset **doubled up** with it — reproduced directly (bostaff and sixshooter swung down near the ankle/hip on both characters through the real equip path; the exact same shared/default `WeaponData` on the same socket landed correctly). Numeric sweep across all 19 shared weapons on both characters confirmed distances were small and byte-identical between characters once using shared data only.

**Two separate mechanisms cause per-character weapon misplacement, not one:**
1. `Boxhead.Player.WeaponHolder.FindHandBone()` prefers a child Transform named exactly `WeaponGripPoint` over the raw `LeftHand` bone, on all four character prefabs (`pfb_char_cowboy`, `pfb_char_ninjamale`, `pfb_char_ninjafemale`, `pfb_char_cowgirl`). This existed *before* this task but was a no-op on Cowboy/NinjaMale/NinjaFemale (socket sat at local identity — zero correction). Only Cowgirl's had ever been given a real (if now-drifted, see below) non-identity value.
2. `Boxhead.Player.WeaponCycler.characterWeaponSets` (on `pfb_player`) resolved a **fully separate, hand-duplicated `WeaponData` asset per character** (`Assets/_Project/ScriptableObjects/Weapons/{Cowboy,NinjaMale,NinjaFemale}/`, 19 assets each) via `WeaponCycler.ResolveWeapon`, matched by the active model GameObject's name (`Cowboy_CharacterModel` etc.). Cowgirl never had a folder — she always resolved to the shared/default set, which is exactly why she never had this bug and served as a clean precedent.

**What round 1 changed:** tuned `WeaponGripPoint`'s real local position+rotation on `pfb_char_cowboy.prefab` and `pfb_char_ninjamale.prefab`, and added a doc comment + `Debug.LogWarning` (on missing-socket fallback) to `WeaponHolder.cs`. Left `WeaponCycler.characterWeaponSets` untouched, "verified" via `WeaponObject_BikeHorn` — which (see above) never actually tested the variant-resolution path.

**What round 2 changed (the actual fix):** removed the `Cowboy_CharacterModel`/`NinjaMale_CharacterModel` entries from `pfb_player.prefab`'s `WeaponCycler.characterWeaponSets`; deleted `Assets/_Project/ScriptableObjects/Weapons/{Cowboy,NinjaMale}/` (38 assets + folder `.meta`s) after confirming via GUID grep that `characterWeaponSets` was the only referencer of any of them; updated `WeaponHolder.cs`'s doc comment to record the retirement and why. Cowboy and Ninja Male now equip purely through shared/default `WeaponData` + their tuned sockets.

**Real, reproduced evidence that rig axis conventions differ per character (not a hypothesis):** the same shared `WeaponData`'s grip offset, applied under an identity `WeaponGripPoint`, landed correctly in Cowboy's hand but floated near Ninja Male's hip, badly rotated (this was round 1's finding, still true — it's *why* the sockets needed different tuned values per character, distinct from round 2's double-offset finding about the now-deleted variant assets). Confirms the project's own asset-pipeline "never assume one rig's axis convention applies to another" rule extends to weapon-grip space, not just import orientation.

**Ninja Female, diagnostic only (not fixed — new model incoming):** her `WeaponGripPoint` is still identity, parented to `mixamorig:LeftHand` (a differently-prefixed rig convention than the other three characters' plain `LeftHand`; `FindHandBone`'s `:LeftHand`-suffix check already handles this, so it isn't itself a bug). She has the pre-round-1 version of this bug (no socket correction at all), not the post-round-1 double-offset version. When her new model lands, tune her socket fresh and retire her `_nf` variant folder in the same pass — don't leave it in place "just in case," since it will very likely double-offset exactly like Cowboy/Ninja Male's did once the socket has real values.

**New-character checklist:** see `docs/BACKLOG.md` B63, item-by-item (add `WeaponGripPoint` under the hand bone → compensate its `localScale` for a non-~1 armature root scale → tune position/rotation live against a *shared* WeaponData, checked against **more than one** weapon shape → bake final values into the **prefab asset**, not just the scene instance → do not create a `characterWeaponSets` entry, and retire one if it already exists once the socket is proven).

Related: [[feedback_play_mode_no_revert]] (the Cowboy `WeaponGripPoint` drift found live during this task — real position+rotation, present in the open Editor's memory, absent from both the saved `.unity` file and the prefab — is a second confirmed instance of that bug, and turned out to be evidence of real prior tuning worth rescuing, not noise to discard). **Round 4 (2026-08-20, later still): first real per-weapon correction, layered on the now-stable socket — kept deliberately separate from the per-character work above.** The owner hand-found correct grip values for the Lasso (`(0.048, -0.19, 0.017)` position, `(-78.971, 23.258, -164.616)` Euler rotation, `0.235` uniform scale) directly on the live weapon instance equipped on Cowboy. Rather than assume a new mechanism, checked `WeaponData.gripPositionOffset`/`gripRotationOffset`/`gripScale` first — that's exactly the field set `WeaponHolder.Attach()` already composes on top of the per-character socket for this purpose. `WeaponData_obj_lasso_equipped.asset` (the shared/default asset, resolved by both Cowboy and Ninja Male since neither has a `characterWeaponSets` entry any more) already had the *rotation* and *scale* fields set to the owner's exact values from some earlier point in this project's history — only `gripPositionOffset` was stale and needed patching. Full detail, tooling notes, and screenshots described in `docs/BACKLOG.md` B63 round 4. Key transferable lesson: **before adding a per-character fix for something that looks wrong on one weapon, check whether the weapon itself already has an existing per-weapon offset field that's simply out of date** — the fix was a single `Vector3` field, not a new prefab/socket change.

**Reusable technique confirmed this round:** `manage_scriptable_object` (`modifyso` action, `target: {path: ...}`, `patches: [{path: "<field>", value: {...}}]`) is the correct tool for a small ScriptableObject field edit — resolves by path or GUID and reports back which it used, no hand-edited YAML needed.

**Important tooling gotcha confirmed this round, worth knowing before testing anything in Play Mode again:** manually rendering a camera via `camera.Render()` + `RenderTexture`/`ReadPixels` inside `execute_code` produces a blank frame of the camera's flat `SolidColor` clear color under URP (this project's pipeline) — it bypasses URP's `ScriptableRenderContext` entirely. Always use `manage_camera`'s own `screenshot` action (its `view_target`/`view_position` params give a positioned close-up without needing custom render code) for any Play Mode visual verification. Separately, `execute_code` calls made *while* Play Mode is running are unreliable — confirmed one call silently ended Play Mode this round (only caught via `manage_scene get_active`'s `rootCount` dropping to the edit-mode count), while a larger single call that did all of one character's setup and synchronously wrote its own file to disk completed fine before Play Mode ended afterward. Treat every `execute_code` call made during Play Mode as possibly-terminal: do the minimum per call, and check `rootCount` immediately after.
