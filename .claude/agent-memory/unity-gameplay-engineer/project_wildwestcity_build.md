**Key technique, worth reusing for any future whole-scene rotation:** this scene's `[ENV - Static]` and `[Player]` are pure organizational parent GameObjects sitting at exactly world-origin position with identity rotation. When that's true, rotating *only those two parent Transforms* (`transform.rotation = Quaternion.AngleAxis(θ, Vector3.up) * transform.rotation`) is mathematically identical to manually rotating every descendant's position around the origin and composing θ onto each one's own yaw (verified live: Unity's `parent.rotation * child.localRotation` composition naturally preserves each building's B78 baked `X=270°` while only adding θ to Y — confirmed Bank `Y 90°→135°`, Blacksmith Forge `Y 270°→315°`, baked X untouched on both). This is strictly safer than the B75/B77 leaf-by-leaf method (impossible to accidentally overwrite a baked rotation, since no leaf transform is ever touched) — check for this shape (identity-transform group parents at the pivot) before doing a leaf-by-leaf rigid rotation on any future scene; it's a big win when available. Also confirms `feedback_baked_transform_compose_rotation`'s lesson generalizes: Unity's Euler decomposition order (Y outermost) means composing a pure-Y rotation via `Quaternion.AngleAxis(θ,Vector3.up) * existing` **always** just adds θ to the Y component and leaves X/Z alone, regardless of how large or unusual the existing X/Z values are — this isn't a special case, it's how Unity's Euler order works, provable in one line rather than needing case-by-case empirical re-verification each time.

**Camera rig ((`pfb_Main_Camera`/`pfb_CM_FollowCam`) deliberately not rotated — checked ground truth via the live `CinemachineFollow` component instead of guessing.** `TrackerSettings.BindingMode = World Space` with a fixed `FollowOffset`: the vcam's actual Play-Mode position/rotation is entirely computed from `FollowTarget.position + FollowOffset` every frame, completely overriding whatever Transform value is authored in the scene. This is the same architectural pattern as `LevelBuilder._cameraYawDegrees` in Room1/AmbushAlley (B75/B77) — a fixed camera reference frame that content rotates underneath, not something that itself rotates with the content. **Lesson: before rotating any camera/vcam object as part of a "rotate everything" task, check whether a Cinemachine Body component's `BindingMode` is World Space (offset is a true world constant, camera transform is cosmetic/overridden) vs. target-relative — this determines whether the camera object's own Transform edit means anything at all.**

**Rotation direction verified primarily via coordinate math, not screenshots — screenshots were genuinely ambiguous at this scene's texture/resolution.** Hand-computed two independent points through the rotation formula and checked them against the standard bird's-eye clock convention (north=+Z up, east=+X right): a point due north swings toward north-east, a point due south (the spawn) swings toward south-west — both unambiguously clockwise. This was the deciding check, not the before/after screenshots (which at this resolution/texture density didn't read clearly either way) — worth defaulting to this method first for any future rotation-direction task, and treating screenshots as a secondary sanity check rather than the primary evidence.

**Real environment quirk hit during Play-Mode verification, distinct from `feedback_unity_mcp_play_mode_capture`: the Unity Editor's Play Mode does not appear to advance simulation frames between separate MCP tool calls when the Editor window isn't focused/active** — `Time.frameCount` stayed frozen across multiple `execute_code` reads until something else (another `execute_code` call) happened to coincide with a real tick; Cinemachine damping relying on elapsed real-frame-time therefore never converges through ordinary polling. **Workaround that worked:** zero the relevant `CinemachineFollow.TrackerSettings.PositionDamping`/`RotationDamping` at runtime (so any single tick snaps fully rather than needing many damped ticks), and if still stuck, directly compute and set the camera's expected position from `FollowTarget.position + FollowOffset` by hand for the one screenshot needed, rather than waiting on frame-by-frame convergence that may never arrive through tool-call polling alone.

**Technique worth reusing for any future circular-arena-clamp sizing on a rectangular level:** raycast-sweep the `Ground` `MeshCollider` from high above (avoids false "void" reads caused by the ray starting inside a building's roof) at fine angular/radial steps to empirically map the *true* void boundary per direction — this is a rectangle's real edge distance, which varies sharply by angle (here: ~20m flank-perpendicular vs ~24m along-street) and is **not** well-approximated by a single "half-diagonal" or "AABB corner" number. Cross-check against `NavMesh.CalculateTriangulation()` vertices (guaranteed-walkable points) to confirm candidate radii don't clip real content, and use `NavMesh.CalculatePath` `PathComplete` to confirm specific far points are genuinely reachable. A single circular radius **cannot** simultaneously reach a rectangle's long-axis ends and stay safely inside its short-axis edges when the rectangle is meaningfully non-square (this street: half-length 24 vs half-width 20) — pick whichever the task's actual required walk-paths demand (here: reaching spawn + the street's north end, both near the long-axis) and accept/document the residual risk in the direction nothing requires reaching (straight past a flank building into the empty margin beyond it). Verify the final choice by reflection-invoking the private clamp method directly on teleported test points in Play Mode (`moved==0` at real destinations, correct clamp-to-radius at a deliberately-out-of-bounds point) rather than trusting geometry math alone.

**Technique note, generalizes beyond this task: CodeDom (this project's `execute_code` default compiler) does not support C# local functions** (`void Foo(...) { }` declared inside a method body) — it's a C# 7 syntax feature CodeDom's C# 6 grammar doesn't parse at all, and it fails with a wall of confusing "unexpected symbol" errors that don't obviously point at the real cause. Use `Func<...>`/`Action<...>` lambda variables instead (`Func<string,int,GameObject> MakeThing = (a,b) => {...};`) — those compile fine since they're just delegate-typed variable assignments (a C# 3 feature), not new syntax.

**Technique note: verifying an event-reactive script (subscribes to a static event, reacts by toggling GameObject/Collider state) does *not* require waiting on a real coroutine-timed gameplay sequence to fire the event.** Directly invoke the private handler method via reflection during a live Play Mode session — e.g. `typeof(WildWestCityZoneDirector).GetMethod("HandleZoneCleared", NonPublic|Instance).Invoke(director, new object[]{0})` — then read the resulting state (`gate.enabled`, `wagon.activeSelf`, etc.) through the same reflection/`SerializedObject` calls used elsewhere. This is faster, deterministic, and doesn't depend on `RoomManager`'s real 0.7s `WaitForSeconds` delay actually ticking — which matters a lot given [[feedback_unity_mcp_play_mode_capture]]: **Play Mode ended silently between tool calls twice in this session** even with no compile happening at the time (a new data point beyond that memory's original "execute_code can end Play Mode" finding — it can also just drop on its own between calls with no apparent trigger). Runtime-instantiated objects (the spawn-point markers, spawned enemy clones) were correctly destroyed on the implicit Stop both times; direct-reflection SetActive/collider.enabled toggles on **pre-existing** scene objects, made through live component references *during* an actual running Play Mode session, were also correctly reverted both times — this project's [[feedback_play_mode_no_revert]] issue affects Inspector/Editor-driven mutations, not necessarily every runtime code path, so don't assume the worst case applies to every kind of Play-Mode change without checking.
