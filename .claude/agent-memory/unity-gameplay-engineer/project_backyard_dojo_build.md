**Two real findings this pass, beyond the geometry itself:**
1. **ADR-0006's `agentClimb: 0.40` claim does not match the live project.** Read directly from `ProjectSettings/NavMeshAreas.asset` and confirmed via `NavMesh.GetSettingsByIndex(0)` at runtime: the project's only agent type (`Humanoid`, id 0) is `agentClimb: 0.75`, unchanged in git history since the very first commit. A 0.35m engawa step is comfortably within that, and `PathComplete` onto the boards was achieved without needing the `agentClimb` change the ADR called a rejected fallback. Built the south-step stepping-stone anyway (cheap, thematically justified, `kutsunugi-ishi`), but the ADR's premise (`agentClimb: 0.40` forcing a ramp) should be corrected at the source next time someone is in it — see [[feedback_verify_adr_navmesh_claims]].
2. **The Stage A cherry tree's visual mesh and its own trunk `CapsuleCollider` were ~7m apart** — trunk correctly at the old arena centre `(0,0,47.5)`, but the visual `CherryTree_BlossomCourt` GameObject's own `localPosition.z` was `54.51`, not `47.5` (confirmed via `Renderer.bounds.center == transform.position` exactly, ruling out a baked-rotation offset explanation — this was a plain placement bug, not a baked-transform gotcha). Fixed by re-centring both objects at the new arena centre `(0,0,55.0)` per the owner's non-negotiable "tree stays at centre" constraint.

**Wall-centreline-vs-inner-face bug caught by the M2 sweep, then fixed:** placing a wall module's centreline exactly ON the authored boundary line (e.g. zone2 apothem 10.0) puts the wall's *inner face* at `authored − half-thickness` (9.85, not 10.0) — M2 clause 1 measures to the inner face. Fixed by offsetting every wall centreline outward by half the wall thickness (0.15m) before tiling, for both the zone1 rectilinear boundary and the zone2 16-gon apothem. Re-verify this on any future arena/boundary build; it's a one-line-easy, invisible-in-a-screenshot, 0.15m error that a strict metric (like M2) will catch and a visual check will not.

**`Rotate(..., Space.Self)` on a 270°X-baked ENV prefab does not compose predictably for non-90°-multiple yaws — this is a NEW instance of the axis-composition risk-class, not the same bug as the wall-tiling one.** See [[feedback_baked_rotation_space_self_composition]].
