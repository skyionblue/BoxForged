Before trusting a backlog/code-review entry's exception diagnosis, sanity-check the claim against the actual field it names. `docs/BACKLOG.md` B102 (filed 2026-08-26, third code-reviewer fix pass) claimed `PlayerController._animator` was "unassigned," throwing `UnassignedReferenceException` every frame. That's impossible on its face: `_animator` (`Assets/_Project/Scripts/Player/PlayerController.cs:60`) is a plain `private Animator` field with **no** `[SerializeField]`, resolved at runtime via `GetComponentInChildren<Animator>()`, and every access is null-guarded. `UnassignedReferenceException` only fires on a serialized `UnityEngine.Object` reference left empty in the Inspector — a non-serialized field can't produce it, and even if it somehow held null, every call site is guarded so it wouldn't throw at all.

**Owner correctly caught this by reading the script themselves rather than trusting the prior pass's verbal diagnosis** — worth remembering: don't accept a "confirmed via console" backlog claim as ground truth for *which field* is at fault without checking that the named field can structurally produce the named exception.

**Re-investigation (4th pass) found the bug doesn't reproduce at all** — not just misattributed to the wrong field, but not currently observable anywhere: ~800 stepped Play Mode frames (idle + a full forced combat encounter to player death, via `RoomManager.ActivateRoom(0)` reflection-invoke + teleporting the player onto a live-spawned enemy) produced zero `UnassignedReferenceException`/`Unassigned*` console entries (`read_console` with `filter_text: "Unassigned"` → 0 hits). A full `SerializedObject` audit of every `UnityEngine.Object`-typed `[SerializeField]` reachable from the live `pfb_player` instance found several genuinely-null fields (`CombatController._hitSparkVFX`/`_parryRingVFX`/`_aerialSlamVfx`/`_parryFlashMaterial`/`_tumbleshotPrefab`, `WeaponHolder.defaultWeaponData`/`weaponPrefab`, `ForgePresenter._imaginationVolume`/`_forgeRevealSfx`/`_upgradeRevealSfx`) but every single usage site is properly null-guarded in code — so none of them can throw either, they just silently skip VFX/audio polish.

**Also found: `Boxhead.Player.WeaponEquipController` carries the only real `[SerializeField] private Animator _animator;` in the entire `Assets/_Project/Scripts/` tree, but it is not attached to any GameObject currently loaded anywhere in the project** (`Resources.FindObjectsOfTypeAll<WeaponEquipController>()` → 0). Looks like dead/superseded code (its own doc comment frames it as an alternate to the live `WeaponHolder`/`CombatController` system) — not investigated further, just worth knowing if it's ever seen attached to something later.

**How to apply:** when asked to root-cause a claimed per-frame exception, (1) read the named field/script first and check the exception type is even structurally possible from that field before doing anything else, (2) reproduce live with a real Play Mode session before trusting an old backlog write-up, using `EditorApplication.Step()` bursts (see [[project_wildwestcity_build]]) to force real elapsed frames, and (3) if it doesn't reproduce after real idle + active-gameplay (combat) exercise, say so plainly rather than inventing a plausible-sounding fix for a bug that isn't there.
