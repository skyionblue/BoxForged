When using the DevUnityMCP `manage_scene` tool for any multi-scene or recovery work:

- **`action: "save"` always saves whichever scene is currently *active* — it silently ignores any `path`/`scene_path` parameter you pass.** There is no save-as. Before ever calling `save`, call `get_active` first and confirm the name/path is exactly the scene you intend — never assume a parameter will redirect it. Getting this wrong once emptied a real scene file to 0 GameObjects (attempted "save to a scratch path" to discard bad in-memory state — it saved over the real file instead) and once wrote an unwanted diff into a protected reference scene that merely happened to be the active one at the time (caught and fixed with `git checkout` on that one file).
- **`close_scene` and `load` both refuse to discard a dirty in-memory scene, and there is no discard/force override** (`force`, `discard_changes`, `discard` — all rejected as unexpected kwargs on this server build). If a scene is dirty and you do *not* want to save it, you cannot close or reload it away. The only way found to neutralize one loaded scene's influence during a shared Play Mode session (e.g., for an A/B comparison against a reference scene) without saving or losing anything: `manage_gameobject` with `set_active: false` on every one of its root objects. This is safe to leave in memory indefinitely — it never touches disk unless something later calls `save` while that scene is active.
- `close_scene` needs `remove_scene: true` to actually detach a *clean* (non-dirty) additively-loaded scene — without it, the scene lingers as an `isLoaded: false` phantom entry that still shows up in `get_loaded_scenes`, and can still contribute active behavior (its global resources — e.g. a baked `NavMesh.asset` — remain in effect even while its GameObjects are inactive).
- `find_gameobjects` and `manage_scene get_hierarchy` are scoped to the *active* scene only, not all loaded scenes — switch the active scene (`set_active_scene`) to inspect a different one.
- **A genuinely dirty scene *can* be force-discarded without saving**, just not through `manage_scene`: use `execute_code` (from the `scripting_ext` tool group — `manage_tools activate scripting_ext` if not already visible) to call `UnityEditor.SceneManagement.EditorSceneManager.CloseScene(scene, true)` directly. The dirty-changes guard is a `manage_scene`-level safety check, not something the underlying Editor API itself enforces. Also useful: `UnityEditor.EditorUtility.RequestScriptReload()` via `execute_code` forces a genuine full domain reload (resets all static/singleton fields like `RoomManager.Instance`) even when no script actually changed — the best way to rule out stale cross-session singleton contamination when a long Editor session has done many Play Mode / scene-load cycles without a real Unity restart.
- **Do not call `execute_code` while Play Mode is active if you need Play Mode to keep running.** Observed repeatedly: a `manage_editor` "stop" call shortly after using `execute_code` mid-session reports `"Already stopped (not in play mode)"` even though nothing intentionally stopped it — Play Mode appears to exit on its own after `execute_code` runs (plausibly because in-memory compilation looks like a script-reload event to the Editor, which auto-exits Play Mode as a safety measure). Confirmed as the same-session cause of otherwise-inexplicable readings (a component's `Follow`/state looking correct one query and wrong the next, a camera position "drifting" between two screenshots that was actually the Editor already back in edit mode). Use `execute_code` freely *before* entering Play Mode or *after* stopping it; while actually testing live Play Mode behavior, stick to `manage_gameobject`/`find_gameobjects`/`manage_camera` screenshot/`read_console` only.

See [[project_room1_v2_build]] for the incident this was learned from.
