Learned/confirmed 2026-08-25 doing a 45° whole-scene rotation on `CulDeSac_WildWestCity` (see [[project_wildwestcity_build]], `docs/BACKLOG.md` B86/B87). Generalizes beyond that one scene — apply these on any future "rotate this room/level N degrees" task.

**1. Check for identity-transform parent groups at the pivot before doing a leaf-by-leaf rotation.** If a scene organizes content under empty GameObjects (e.g. `[ENV - Static]`, `[Player]`) that themselves sit at exactly the rotation pivot with identity rotation, rotating *only that parent's Transform* (`transform.rotation = Quaternion.AngleAxis(θ, Vector3.up) * transform.rotation`) is mathematically identical to manually rotating every descendant's position around the pivot and composing θ onto each one's own yaw — Unity's hierarchy math does the composition for free, for every descendant, in one call. This is strictly safer than a leaf-by-leaf pass (used in `CulDeSac_Room1_v2`/`CulDeSac_AmbushAlley_v2`, B75/B77) because no leaf transform is ever touched, so there's no way to accidentally overwrite a baked rotation on a leaf prefab (see [[feedback_baked_transform_compose_rotation]]) — verify the parent really is at the pivot with identity rotation first (read it live, don't assume), then verify a couple of descendants' post-rotation world transforms by hand-computing the expected values and comparing.

**2. This also proves the "compose, don't overwrite" rule is not case-by-case — it's structural.** Unity's Euler decomposition order is Y-outermost (`Quaternion.Euler(x,y,z) = Qy(y)*Qx(x)*Qz(z)`), so left-multiplying by an additional pure-Y rotation (`Qy(θ) * existing`) **always** just adds θ to the existing Y euler component and leaves X/Z untouched, no matter what the existing X/Z values are (baked 270° tilts included). This can be derived once rather than re-verified empirically per prefab batch — useful confidence when a scene mixes several different baked-rotation defects.

**3. Before rotating a Cinemachine camera/vcam object as part of "rotate everything," check the Body component's Binding Mode.** If it's World Space (or similar — a fixed offset independent of the Follow target's rotation), the vcam GameObject's own scene-authored Transform is cosmetic only; Cinemachine recomputes `FollowTarget.position + FollowOffset` every frame in Play Mode and fully overrides whatever the Transform holds. Rotating that Transform anyway is harmless but functionally meaningless and can be misleading in the Scene view. This is architecturally the same shape as `LevelBuilder._cameraYawDegrees` in Room1/AmbushAlley — a fixed camera reference frame that content rotates underneath, not something that rotates with the content. Leave it un-rotated and say why, backed by the live component read, rather than rotating it "to be safe."

**4. Prefer coordinate math over screenshots to verify rotation direction (clockwise/counterclockwise, "left"/"right").** Hand-compute two independent reference points through the applied rotation formula and check them against the standard bird's-eye map convention (north=+Z up, east=+X right, clockwise = N→E→S→W increasing). A point that starts due north should swing toward north-east under a correct "rotate right" transform; a point due south should swing toward south-west. This is fast, unambiguous, and — at this project's actual texture/resolution — was strictly more reliable than comparing before/after screenshots, which can be genuinely hard to read by eye on repetitive environment art. Use screenshots as a secondary sanity check, not the primary evidence, and note in the report that the math was the deciding check.

**5. Unity Editor Play Mode in this environment does not reliably advance simulation frames between separate MCP tool calls when the Editor window isn't focused.** `Time.frameCount` can sit frozen across several `execute_code` polls; Cinemachine damping that depends on elapsed real frame-time may never visibly converge through ordinary polling, even though `isPlaying` is true and `timeScale` is 1. If a Play-Mode screenshot needs a settled/converged camera, don't wait-and-poll — zero the relevant damping fields at runtime so any single tick snaps instantly, and if still stuck, directly compute and set the expected camera transform by hand (e.g. `FollowTarget.position + FollowOffset`) for the one screenshot needed. This is a distinct failure mode from [[feedback_unity_mcp_play_mode_capture]] (which is about Play Mode silently ending) — this one is about Play Mode running but not ticking between calls.

**6. A rigid rotation can surface latent, unrelated scene bugs that only show up once you actually verify in Play Mode — root-cause before assuming your own edit broke something.** Rotating this scene's content exposed `PlayerController._arenaBoundaryRadius` defaulting to 8.5m centered at world origin while spawn sits ~58m out — a pre-existing mismatch (true before and after the rotation, since a rigid rotation preserves distance-from-origin exactly) that was never triggered before because Play Mode hadn't actually been exercised on this particular spawn distance. Confirmed via live `SerializedObject` read that the instance never overrode the script's defaults, which is what proved it wasn't something this session's edit caused. Worked around non-destructively (temporary runtime-only reflection edit, confirmed to revert cleanly on Stop) to get the required verification screenshot, and filed it as its own backlog item rather than silently patching the shared `PlayerController` script mid-task.
