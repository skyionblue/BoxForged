Discovered 2026-08-20 while root-causing B60 (`docs/BACKLOG.md`) — the `RunStartUI` character-select screen stopped appearing in `CulDeSac_Room1_v2` with no code change and no on-disk scene diff to explain it.

**The behavior:** normally, Unity's default "Enter Play Mode Settings" take a scene snapshot when Play starts and restore it exactly when Play stops, so anything a script (or a person, via the Hierarchy) toggles *during* Play — `SetActive`, transform moves, etc. — vanishes the instant you press Stop. This project's Editor does **not** do that. Confirmed directly, twice, in the same session: (1) a `GameObject.SetActive(true)` fix I applied via `execute_code` *before* entering Play survived a full Play→Stop cycle into Edit mode (expected either way, since it wasn't a Play-time change). (2) more tellingly, `pfb_player`'s root local position drifted from its committed `(0,0,0)` to `(0,0,-2.5)` and the scene's `isDirty` flag flipped `true` purely from entering and exiting Play Mode with **no input sent and no script explicitly moving it** — that drift, and the flag, both persisted after Stop with no revert.

**Why this matters:** any Play Mode session — mine or a previous one — can leave permanent, invisible (until someone runs `git diff` on a *saved* scene, or inspects live state) landmines in the currently-open Editor's in-memory scene: a `SetActive(false)` toggled to get past a blocking UI screen while testing something unrelated, a physics-settled position, anything. It leaves **zero trace** in `git status`/`git diff` unless someone happens to save afterward — which is exactly what made B60 look like a mysterious code-or-scene regression when it was neither. **Confirmed, not just inferred:** [[project_room1_v2_build]]'s own log from earlier the same day states outright — "worked around by deactivating `pfb_hud_v4` directly to unblock the camera for screenshots" — while testing the forge VFX flow and getting blocked on the `RunStartUI` picker with no UI-click tool available. That deactivation was never undone, and because of this exact behavior, it silently carried forward into the owner's next fresh Play session.

**How to apply:**
- When a bug "makes no sense" against the code and the saved scene file both, suspect **live in-memory Editor state** next, before suspecting a subtler code path. Check via `execute_code` (walk the actual live object graph — see [[feedback_unity_mcp_gameobject_lookup]]) rather than only reading the `.unity` file on disk.
- Before trusting any diagnosis, check whether the current scene's `isDirty` is `true` via `manage_scene` `get_active` — if so, the in-memory state may not match disk, and may not match what you'd get from a genuinely fresh load either.
- After finding and fixing a live-state bug like this, **reload the scene from disk** (`manage_scene` `load` on the same path) and re-verify from a demonstrably clean (`isDirty: false`) state before calling it done — don't just trust the in-memory fix, since the same "doesn't revert" behavior that caused the bug could just as easily be hiding a leftover problem behind your own fix.
- Before any `save`, diff what's about to be written (`git diff` after saving, or compare live values against the last-known-good committed values first) — a Play Mode session run *during* investigation can silently bake in unrelated drift (exactly the `pfb_player` position drift found alongside the real B60 fix) that would otherwise get committed as if it were intentional.
- Do not assume this is an isolated one-off: if the project's Enter Play Mode Options truly have scene-reload-on-stop disabled (most likely explanation), this can happen again in any future session, for any GameObject, not just HUD/`RunStartUI`.
