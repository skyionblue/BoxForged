---
name: feedback-baked-rotation-space-self-composition
description: Transform.Rotate(Space.Self) on an object with a baked non-identity root rotation (e.g. the dojo/CulDeSac ENV prefabs' 270°X import correction) does not compose into the clean (baseX, yaw, 0) form except at 90°-multiple yaws — use a temp identity-rotation rig to compute the correct localRotation instead.
metadata:
  type: feedback
---

**Rule:** to place a prefab with a baked non-identity root rotation (e.g. the World1/World2 ENV kit's near-universal 270°X FBX-import correction) at a specific *design-space facing yaw*, do not call `transform.Rotate(0, yaw, 0, Space.Self)` on the already-instantiated, already-rotated object. Instead: instantiate under a **temporary identity-rotation parent** (a plain `new GameObject()` at scene root, not nested under any rotated hierarchy), apply the desired yaw via `Space.World` there (World == Local when the parent is identity), read the resulting `transform.localRotation`, destroy the temp rig, and apply that captured rotation directly to the real object's `localRotation`.

**Why:** verified empirically on `pfb_env_bld_shedwithcrate` (baked default `(270,180,0)`) and `pfb_env_target_dummy` (baked default `(270,0,0)`) in `Backyard_Dojo.unity` during the B116 re-layout. `Rotate(Space.Self, yaw)` happened to produce the expected clean `(270, yaw, 0)`-shaped result for `yaw` values that are multiples of 90° (confirmed working for the weapon rack at yaw=90, and for the shed needing a 90° correction) — but for arbitrary yaws (e.g. 20°, 340°, 15°) it produced garbage like `(290, 270, 270)` or `(0, 90, 90)`, a different combined rotation with no simple relationship to the requested facing angle. The composition `R_x(270°) · R_y(θ)` only decomposes back into a clean `(270°, θ, 0°)` Euler triple for special-case θ (90°-multiples happen to work because they're exactly where the axis permutation stays clean); general θ does not decompose that way at all, and the resulting object silently faces a *completely wrong and non-obvious* direction (or, worse for a footprint-shaped object like a shed, has the wrong world-axis-aligned bounding box entirely — `Renderer.bounds.size` came back `(11.947, 6.383, 11.947)` — square and wrong — instead of the correct `(7.401, 6.383, 9.495)`).

**How to apply:** any time a placement helper needs a *non-90°-multiple* yaw on one of these baked-rotation ENV prefabs (facing angles for makiwara/lantern-type decorative props are the common case — wall/structural pieces are usually axis-aligned or handled by the wall-tiling helper's own `Atan2` convention, a different and already-documented risk, see [[feedback_wall_tiling_yaw_axis_mismatch]]), use the temp-rig technique above. It is cheap (instantiate+destroy one throwaway GameObject) and removes the guesswork entirely — verify with a bounds/orientation check afterward if the prop's footprint is asymmetric (like the shed), since a silently-wrong-but-plausible-looking rotation on a small symmetric post is much easier to miss than on a shed. This is a *different* failure mode from [[feedback_wall_tiling_yaw_axis_mismatch]] (that one is about the wall-tiling helper's own `Atan2(dir.x,dir.z)` convention putting length on the wrong local axis) — this one is about `Transform.Rotate`'s `Space.Self` composing unpredictably on top of an already-non-identity baked rotation. Both live in the same "270°X-baked ENV prefab" danger zone and both are invisible in a cursory screenshot.
