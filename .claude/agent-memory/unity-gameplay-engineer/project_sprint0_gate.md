**UPDATE 2026-08-19 (later same day): B27 follow-up implemented.** `docs/BACKLOG.md` B27 (camera lateral-width floor fails below ~20:9 aspect) carries an explicit owner decision — "DECIDED: build the aspect-adaptive fix... queued as a scoped follow-up engineering task" — so a task briefing that names B27/ADR-0001 by number and quotes that decision is implementing already-authorized backlog work, not opening a new production sprint; no separate go-ahead needed beyond the SPRINT.md status-line check. Implemented as `Boxhead.Core.AspectAdaptiveCameraFraming` on `pfb_CM_FollowCam.prefab`: uniformly scales `CinemachineFollow.FollowOffset` (never pitch/FOV) to hold the >=16m lateral-width floor on narrow aspects. Key derivation worth remembering for similar fixed-pitch-camera math: scaling the whole offset vector by one factor preserves pitch exactly (height/setback ratio unchanged), and the top-ray angle (`pitch - verticalFOV/2`) is distance-independent — so this class of fix can never accidentally bring the horizon into frame, which simplifies the acceptance-criteria check considerably.

**UPDATE 2026-08-20: over-the-shoulder lateral offset added, plus a real bug found in `AspectAdaptiveCameraFraming`'s distance math.** Owner asked for the camera pulled back and shifted right (still no yaw/rotation — a pure world-space +X `FollowOffset` translation, since a fixed-yaw camera's frustum footprint just slides sideways in world space when you add lateral offset, without changing shape). Final values landed via live iteration during the session (owner watched a screenshot and asked for "further right and pulled back a little more" beyond the first-pass numbers) — settled on `FollowOffset = (2.25, 7.425, -10.22)`, up from `(0, 5.5, -7.57)`. **The bug:** `AspectAdaptiveCameraFraming` computed its base "view distance" as `_baseFollowOffset.magnitude` — the full 3D magnitude. That's correct only when X=0. The moment X is non-zero, magnitude inflates above the true pitch-plane slant distance (`sqrt(y²+z²)`), which under-corrects the scale needed to hit the width floor on narrow aspects. Fixed by computing base view distance from `(y,z)` only, and extracted the whole calculation into an internal static `ComputeScaledOffset(...)` pure function (no MonoBehaviour dependency) for future testability — this project has zero test infrastructure today (no `Tests` asmdef anywhere), so no automated test was actually wired up, but the function is now shaped to make adding one trivial later. **Geometry worth remembering for any future asymmetric-offset work:** adding lateral X to a fixed-yaw FollowOffset does NOT change F (ground ahead), R (ground behind), or the top-ray angle at all — those depend only on height/depth-setback (Y/Z), since X is a pure sideways translation orthogonal to the pitch plane. It also does NOT change total lateral width W. What it does do is shift *where* that width band sits relative to the player: left-half = W/2 − X, right-half = W/2 + X. Scaling X proportionally along with Y/Z (same `scale` factor) is the *correct* choice, not an approximation — it keeps the player's off-centre fraction-of-frame constant across aspects rather than letting a fixed-metre offset shrink in relative terms as the rig pulls back on narrow screens, and since scale is always ≥1, it can only ever grow both side-widths, never shrink them below their un-scaled values.

**Also found and fixed in the same pass:** `CulDeSac_Room1_v2.unity` had a stray `PrefabInstance` override on `FollowOffset.y`/`.z` (not `.x`) that matched neither the ADR nor the prefab — almost certainly a `AspectAdaptiveCameraFraming` Play-Mode-computed value that got baked into the scene by an earlier session (same family of risk as [[feedback_unity_mcp_scene_save_safety]]). It silently overrode whatever the prefab said for that one scene. Removed. Worth spot-checking other scenes for the same drift before trusting a prefab's authored `FollowOffset` is what's actually live in a given scene — always verify with `execute_code` reading the live component, not just the prefab file.

**UPDATE 2026-08-20 (same session, third iteration): direction change from over-the-shoulder offset to a genuine yaw rotation, after owner sent a mobile-Hades reference image.** This is architecturally different from iterations 1-2 (lateral X shift only) — the fixed rig's yaw itself moved off 0°, tried 35°. Two things worth remembering for any future non-zero-yaw work on this rig:

1. **`CinemachineFollow`'s WorldSpace `BindingMode` adds `FollowOffset` in raw world axes, completely independent of the vcam's own rotation.** So rotating the camera's authored `Transform` rotation alone, without also rotating `FollowOffset`'s horizontal (X,Z) component by the same yaw, decouples position from view direction — the camera would keep sitting on the old straight-behind axis while aiming down a new diagonal one. The fix is a rigid rotation of the offset's horizontal component by the new yaw (`Quaternion.Euler(0,yaw,0) * offset.xz`), which is magnitude-preserving and keeps the lateral "camera's-right-of-boresight" shift intact in the new frame. Verified via `Quaternion.Euler`/`Vector3` math directly through `execute_code` rather than by hand — cheap and removes rounding-error risk in the prefab file.

2. **F/R/W/top-ray are camera-relative, not world-axis-relative — yaw doesn't change any of B59's acceptance numbers.** They come from pitch, height, vertical FOV, and horizontal FOV only. This means a yaw change is "free" with respect to the acceptance criteria already validated for a given `FollowOffset` magnitude/lateral-split — but **`LevelBuilder.ValidateCameraClearance` is NOT camera-relative**, it had a `Vector3.back`-hardcoded "behind" raycast direction (with its own comment admitting the yaw=0 assumption). Fixed by adding a serialized `_cameraYawDegrees` field and deriving the raycast direction from it at validation time — this must be kept in sync with the rig's real authored yaw per-scene (same manual-sync burden the old hardcoded constant already silently had; now it's visible and settable instead of silently wrong). Any future camera-geometry work should specifically check for other hardcoded `Vector3.forward`/`.back`/`.right` assumptions baked in elsewhere under the "yaw is always 0" premise — this was the second one found (the first, `CameraBehindDirection`) and there could be more (occlusion/minimap/HUD-facing code is a reasonable place to check next, though not checked yet).

**Also found (third occurrence in one session) of the override-drift pattern:** `CulDeSac_Room1_v2.unity`'s `pfb_CM_FollowCam` instance had hard `PrefabInstance` overrides pinning `m_LocalRotation.x/y/z/w` to the old yaw-0 quaternion, which silently masked the prefab's new rotation exactly the way the `FollowOffset.y/z` override masked iteration 1's pull-back. **Always verify a live component's actual values via `execute_code` after any prefab edit that touches this camera rig, in this specific scene — don't trust the prefab file alone.** Given three occurrences now, treat "does this scene have a stray override on the camera rig" as a standing thing to check, not a one-off surprise.

**UPDATE 2026-08-20 (same session, second iteration): first pass under-corrected on both axes — owner said `(2.25, 7.425, -10.22)` still felt "really really close," wanted a meaningfully bigger jump, not a small nudge.** Landed on `FollowOffset = (3.75, 10.02, -13.79)` — roughly another 35% pull-back beyond iteration 1 (total ~82% further back than the original ADR rig's `9.36m` view distance, now `17.05m`), plus lateral X raised from 2.25 to 3.75. Confirms the general lesson: when an owner says a first correction under-shot, jump by a real multiplicative step on the *next* pass rather than repeating a similar-sized nudge — this is the second time in one session the same axis needed a bigger correction than the initial suggested range. Worth checking left/right-width math fresh at every iteration, not just trusting the ratio held: at this much pull-back, `AspectAdaptiveCameraFraming` stopped engaging entirely across the whole 4:3-21:9 range (the base rig alone now clears the 16m width floor everywhere), so the worst-case left-side width is no longer floor-clamped — it's purely `(aspect-driven total width)/2 − X`, smallest at 4:3. Re-derive this per iteration rather than assuming a previous "runtime component engages here" boundary still applies once the base offset has moved.
